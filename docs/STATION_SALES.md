# Продажи сайта и агентов по станциям

Отдельный отчёт АИС `/station-sales` — таблица «Сводный отчёт по продажам с
сайта Автовокзал57.рф и агентами в разрезе станций» из `htdocs/ais/in.php`.
Сохранены все 20 колонок, их порядок, итоги и условия расчёта по станциям.
Сайт читается из нового Postgres `avtovokzal`, копия продаж станций хранится
в Postgres `ais`. При формировании отчёта подключения к Firebird нет.

## Как пользоваться

Период сверху — период отчёта. Фильтр станции ограничивает строки и итоги
отчёта. Ниже отдельный блок обновления: отметьте одну, несколько или все
станции и нажмите «Обновить выбранные станции». Незавершённое задание той
же станции второй раз не создаётся. Можно закрыть вкладку: сбор продолжится.
Открытая страница показывает прогресс и обновляет уже сформированный отчёт
после публикации суток.

Без своего периода сбор идёт от «сегодня минус N дней» до сегодня
включительно. **N задаётся в `/settings`, поле «Глубина обновления продаж по
станциям и агентам»**, ключ `station_sales_lookback_days`, диапазон 1–3650,
начальное значение 90. То же значение используется автоматическим сбором
каждый час. Изменение применяется к следующим заданиям; уже выполняемое
задание продолжает своё окно. Настройки кэшируются на 30 секунд.

Флажок «Указать свой период продаж» позволяет пересчитать архив. Это даты
**операций продажи/возврата SALE.DATESALE**, а не даты поездки. Для ведомости
за выбранный месяц могут потребоваться билеты, проданные раньше месяца.
Прежние данные за пределами обновляемого окна сохраняются.

По каждой станции видны:

- актуальность последнего полностью собранного текущего окна и его границы;
- последний успешно пересчитанный период, в том числе архивный, и время завершения;
- состояние последнего задания, число обработанных дней/строк и ошибка.

Актуальность — московское время **начала** успешного сбора: сегодняшний день
читается первым, поэтому время завершения всего окна обещало бы лишнюю
свежесть. Пересчёт прошлого периода и прерванное обновление эту отметку не
двигают. После увеличения глубины или смены дня прежняя отметка остаётся
видимой, а страница сообщает, что новое окно ещё не собрано полностью.

## Устойчивость сбора

`station-sales:sync` создаёт задания в `station_sales_sync_runs`, а
`station-sales:work` обрабатывает их порциями. Ofelia запускает постановку
каждый час, обработчик — каждую минуту. Одна станция может иметь одно
незавершённое задание; проверка защищена блокировкой строки состояния.

Каждая порция — до 250 строк одной станции за один день. Чтение выполняется
в отдельном PHP CLI-процессе с памятью 128M и жёстким дедлайном 25 секунд:
это ограничивает не только TCP connect, но и зависшие PDO execute/fetch.
Обычный проход обработчика ограничен 50 секундами. Веб-запросы сбора не
ждут; лимиты nginx/php-fpm для обновления не задействуются.

Пагинация идёт по полному восьмипольному PK SALE. Доли секунды TIMESALE
сохраняются строковым CAST при чтении и инлайном проверенного времени в
курсоре: PDO Firebird обрезает их и при чтении TIME, и при биндинге.
Все поля исходной строки, включая неизвестные новой АИС, сохраняются в
`raw_data`; расчётные поля имеют отдельные колонки и индексы. Глобальный
ключ совпадает по смыслу с PK прежнего SALE_ALL: реплика одной продажи в
двух базах не удваивает итог.

Порции сначала сохраняются в `station_sales_staging`. Только полностью
прочитанные сутки атомарно заменяют соответствующие данные в
`station_sales`; пустые сутки также считаются успешно прочитанными.
При ошибке незавершённые сутки не публикуются, готовые сутки остаются,
станция получает статус ошибки, остальные задания продолжаются.
Повторный запуск обновляет данные без дубликатов. Курсор и lease в БД
позволяют продолжить сбор после перезапуска сервера; истёкшая lease
подхватывается через две минуты. Поздний ответ прежнего обработчика не
может опубликовать данные с уже заменённой lease.

## Расчёты

Продажи сайта считаются по `orders.total_price` оформленных заказов, что
сохраняет страхование старых заказов. Для импортированных заказов
сохраняется исходное условие `legacy.status = 1`. Возвраты учитываются по
фактическому возврату денег; их исходная стоимость включает страхование
из `refunds.legacy.strah`. Отдельные возвраты багажа учитываются своей
стоимостью, возвраты удержаний уменьшают КРЗ без повторного вычитания
стоимости билета. Ведомость сайта считает поездки и стоимость возвращённых
билетов по датам поездки; предварительная продажа — поездки после конца
отчётного периода, оплаченные в этом периоде.

Условия станционных колонок сохранены из исходника:

| Показатель | Условие |
| --- | --- |
| Ведомость сайта по базе станции | `AWTCODSALE=9984`, дата поездки в периоде, `TYPE_OPER=0`, `TICK_BACK=0` |
| Агентские в ведомости | то же, `AWTCODSALE IN (9999,9900)` |
| Агентские продано | дата продажи в периоде, `TYPE_OPER=0`, `KKM_OK=1` |
| Агентские возврат | дата продажи в периоде, `TYPE_OPER>0`, сумма `PRICE_PLACE+PRICE_BAG` |
| Агентские стоимость возвращённых | **только `PRICE_PL_ISX`**, как исходный `AGENTBACK`, без `PRICE_BAG_ISX` |
| Агентские КРЗ | стоимость возвращённых минус сумма возврата |
| Агентские предварительные продажи | агентские продажи, дата поездки после периода |
| Агентские возврат предварительных | дата операции в периоде, поездка после периода, `TYPE_OPER>0`, сумма `PRICE_PL_ISX+PRICE_BAG_ISX` |

Не добавлялись отсутствующие в legacy фильтры `IS_PRN`, `MAY_BACK`,
`TYPE_TICK` и т. п.: они изменили бы суммы. Денежные производные показатели
и итоги складываются в целых копейках.

## Выкладка и перенос архива

После выкладки кода нужны миграция АИС, сборка SPA и перечитывание заданий:

```bash
docker compose exec -T ais_app php artisan migrate --force
docker compose run --rm --no-deps ais_spa sh -lc 'npm install && npm run build'
docker compose restart ais_spa scheduler
```

Новый отчёт автоматически доступен системным администраторам. Для других
ролей выдаются `report:station-sales.view` и, отдельно, право
`report:station-sales.refresh`. Обновление не требует кода подтверждения,
из сессии «от имени сотрудника» запуск запрещён сервером.

Для начального переноса прежнего `SALE_ALL`:

```bash
docker compose exec -T ais_app php artisan station-sales:import-legacy
```

По умолчанию читается локальная Firebird `firebird:ais`. Для другой копии
задайте в `ais-api/.env` переменные `LEGACY_AIS_DB_HOST`,
`LEGACY_AIS_DB_PORT`, `LEGACY_AIS_DB_NAME`, `LEGACY_AIS_DB_USER`,
`LEGACY_AIS_DB_PASSWORD`. Команда читает архив по 1000 строк дочерними
процессами с тем же дедлайном, сохраняет курсор в `storage/app` после каждой
порции и продолжает с него при повторном запуске. `--pages=10` ограничит
число порций одного запуска; `--restart` перечитает источник с начала.
Существующие строки не перезаписываются, поэтому архив не затирает данные,
которые уже собраны с живой станции. Импорт не выставляет актуальность
станций. Исходная Firebird остаётся без изменений.

Ручной запуск очереди и обработчика:

```bash
docker compose exec -T ais_app php artisan station-sales:sync --stations=5701,5706
docker compose exec -T ais_app php artisan station-sales:sync --stations=5706 --from=2026-10-01 --to=2026-10-31
docker compose exec -T ais_app php artisan station-sales:work
```

Проверки: `docker compose exec -T ais_app php artisan test --compact --filter=StationSales`
проверяет формулы, настройки, выбор станций, сохранение актуальности,
атомарную публикацию, повторный сбор, возобновление после обрыва, права и
реальное прерывание зависшего дочернего процесса.

Дополнительная сверка всех 19 денежных колонок с оригинальными запросами
Firebird (нужны перенесённый архив и обе прежние базы `site`/`ais`):

```bash
docker compose exec -T ais_app php tests/Integration/compare-station-sales-legacy.php 2026-06-01 2026-06-30
```

На локальной копии за июнь 2026 проверено 38 показателей по двум
настроенным станциям, расхождений нет. Перенесено 968 082 строки архива.
