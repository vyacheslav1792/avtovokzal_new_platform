# CLAUDE.md — avtovokzal_new_platform

Инструкции для Claude Code по работе с этим репозиторием. Читай вместе с
[README.md](README.md), [PLAN.md](PLAN.md) и [docs/LEGACY.md](docs/LEGACY.md) — здесь только
то, что не выводится из кода: правила, ловушки и как что запускать.

## Что это

Модернизация АИС автовокзалов. Три легаси-компонента (сайт `avtovokzal57`, АИС `ais`,
API продаж `ais/api`) переводим на **PHP 8.5 / Laravel 13 / Nuxt / PostgreSQL 17** в Docker
Compose. Вендорные Firebird-базы продаж (BUSTER и др.) **не трогаем** — структура вендорная.
Идёт **этап переноса**: покупка, возврат по коду, печатные формы и фискализация уже
работают на новом стеке (сквозные прогоны 2026-08-03); статус по этапам — в PLAN.md.

## Правила (обязательно)

- **НЕ упрощать функциональность legacy при переносе без ЯВНОГО разрешения
  пользователя** и не делать допущений, не соответствующих реальности
  («аналог», «примерно то же») — изучить исходник целиком, найти все отличия
  и воспроизвести. Если кажется, что что-то можно упростить/выкинуть —
  сначала спросить. Явно разрешённые упрощения фиксировать здесь
  (разрешено: защитный код 123321 в back_bilet.php не переносим —
  позже будет нормальная авторизация; IP-ограничения агентов в legacy
  на локальном контуре убраны).
- **Боевой legacy-код правим ТОЛЬКО в локальной копии `./htdocs`** (распакованный бэкап).
  Никогда — на CIFS-шаре `/mnt/htdocs`.
- **На шаре `/mnt/htdocs` НЕ использовать `perl -i` / `sed -i`** — файл удаляется. Только
  прямая перезапись через Write. (См. память `cifs-no-inplace-edit`.)
- **Именованные тома Docker не используем** — только bind mounts (`./data`, `./htdocs`, …).
- **`dist/` и `data/postgres/` не коммитим** — это артефакты сборки/данные.
- **Тестовая покупка билета:** всегда с багажом, по 2–3 билета за раз. При неоднозначности —
  **остановиться и спросить** пользователя.
- Тестовые креды (SMB `admin/avtovokzal57`, шлюз Сбербанка `metagraphica/metagraphica`,
  тест-карта) — только для локальной разработки, наружу не публиковать.

## Окружение

```bash
docker compose up -d          # поднять стек
docker compose ps             # статус
docker compose logs -f <svc>  # логи
docker compose down           # остановить (данные Postgres в ./data сохранятся)
```

**Публичный адрес сайта — одна переменная `SITE_URL` в корневом `.env`.**
Compose раздаёт её сервисам (`docker-compose.yml`): `FRONTEND_URL` у `app`,
`SITE_FRONTEND_URL` у `ais_app`, `NUXT_PUBLIC_SITE_URL` у `frontend`,
`VITE_SITE_URL` у `ais_spa`; в проде то же значение идёт и в
`NUXT_PUBLIC_API_BASE` (API живёт на том же домене). Из `FRONTEND_URL`
выводятся адрес возврата платёжного шлюза (`services.sberbank.return_url`) и
`redirect_uri` VK — отдельные `SBERBANK_RETURN_URL` / `VK_REDIRECT_URI`
нужны только когда возврат должен идти на другой адрес. **Ловушка:**
переменная окружения контейнера перекрывает одноимённую строку в
`backend/.env` (Dotenv не перезаписывает уже заданные переменные) — правка
`FRONTEND_URL` в `backend/.env` на поднятом стеке ничего не изменит, менять
нужно `SITE_URL`. После правки — `docker compose up -d` (не `restart`:
окружение задаётся при создании контейнера).

Порты: web :8088 (backend, высокоуровневое API avtovokzal57; **был :8080** —
переехали 2026-08-14, на хосте его постоянно держит vite соседнего проекта,
и контейнер `web` не поднимался), sales_web :8085
(**API продаж**, `sales-api/`, отдельная БД Postgres `sales`), kkm_web :8087 (**KKM API**,
`kkm-api/`, БД Postgres `kkm`), ais_web :8086 (**AIS API**, `ais-api/`, БД Postgres `ais`;
:8082 на хосте занят посторонним Apache), frontend :3000 (Nuxt + Nuxt UI), ais_spa :3001
(SPA отчётов АИС), db :5432, firebird :3050, legacy АИС :8090 (`ais/`), legacy сайт :8091
(`avtovokzal57/`).
**KkmServer** установлен на хост-машине (НЕ docker): systemd `kkmserver.service`,
http://127.0.0.1:5893, виртуальная ККТ NumDevice=1 (эмулятор); из контейнеров доступен
как `host.docker.internal:5893` (extra_hosts host-gateway у kkm_app).
Таблица сервисов — в README.

### Новые сервисы (этап переноса, август 2026)
- **`sales-api/`** — API продаж (Laravel 13): рейсы/места/резерв/продажа/возврат через
  процедуры KS_* Firebird. Работает автономно, без оплат. Журнал всех запросов/ответов —
  Postgres `sales.api_requests`; резервы/продажи/возвраты — свои таблицы. Агенты — Bearer-токен
  (`config/agents.php`) + IP whitelist. Ловушка ID_TIME_PLACES (доли секунды) решена инлайном
  литерала (`BusterConnection::quoteTimestamp`). `GET /trips` без `date` — режим
  «ближайшие» legacy (`blij=1`): рейсы всех дат от сегодняшней, `first 200`;
  `for_sale=0` отдаёт и рейсы, недоступные к интернет-продаже. Ограничения
  продажи по дальности (`min_kilom`/`max_kilom`) считаются после выборки по
  TRACES — как в legacy; ручное перекрытие SALE_BOUND_AFTER (legacy-файл
  `vidjets/ogranichenie.txt`) переехало в `config/sale_bounds.php`.
  **Список пунктов назначения (`GET /stations/{awtcod}/destinations`) сортируется
  в PHP** (`App\Support\StationNameSorter`), а НЕ в запросе: KS_STATIONS отдаёт
  порядок базы — с учётом регистра и знаков, поэтому «АЗС», «СХТ», «ДРСУ-3»
  вставали в начало группы, а «пов.Вепринец», «м-н Москва», «ул. Заводская» —
  в самый конец. Ключ сортировки: нижний регистр, ё→е, всё кроме букв и цифр —
  разделитель, лишние пробелы убраны; сравнение Collator `ru_RU` (без ext-intl
  фолбэк на побайтовое — после нормализации порядок тот же). Та же логика
  добавлена в legacy (`ais/api/sort_help.php` + `api2.php`, выложено на бой
  2026-08-14 с бэкапами `*.bak_20260814`), порядок сверен построчно на боевых
  списках. Селекты сайта менять не пришлось: Nuxt UI при вводе поднимает
  совпадения с начала названия и сохраняет порядок сервера внутри групп; в
  legacy для этого понадобилась своя `score` у selectize (`js/main.js`), иначе
  найденное сортировалось по релевантности — короткие названия вперёд.
- **`backend/`** — высокоуровневое API: заказы (`orders`), оплата Сбербанк через SDK
  `voronkovich/sberbank-acquiring-client` (локально тестовый контур 3dsec/metagraphica),
  подтверждение оплаты + оформление, возврат по коду (`refunds/preview|confirm`, таблица
  `refunds`, подписанный Crypt-токен подтверждения), данные печати (`orders/{id}/print`,
  обезличивание 30 дней), билеты одним PDF (`orders/{id}/pdf`).
  **Незавершённые покупки** (`POST orders/pending`): покупатель ушёл на шлюз и не
  вернулся — заказ есть, билетов нет. Заказ ищется по идентификаторам из
  `localStorage` браузера И по `user_id` (у кабинета — с любого устройства);
  состояние считается по статусу заказа и `getOrderStatusExtended` шлюза:
  `awaiting_confirmation` (деньги у нас, билетов нет) или `awaiting_payment`
  (ещё можно оплатить, пока жива бронь). Срок оплаты — минимум из
  «создан + 24 мин» (столько держит `KS_BRONTIME_PLACE`) и «отправление −
  32 мин». В legacy это жило в PHP-сессии и умирало вместе с ней.
  **Правило детского тарифа** (`config/sale_rules.php`, `CHILD_TARIFF_REQUIRES_ADULT`
  и `MAX_CHILDREN_PER_ADULT`): детский билет только вместе с полным, не более N
  на взрослого — перенос legacy (`js/passengers.js` + `url/passengers.php`),
  но выключаемый. Форма покупки читает те же значения через
  `GET /api/v1/sale-rules`. Пункт «Детский» из списка НЕ убираем — исчезнувший
  пункт покупатель не заметит и не поймёт, почему детского билета нет; вместо
  этого выбор не применяется и показывается уведомление с текстом legacy.
  **Брошенные покупки** — команда `orders:cancel-abandoned` (ofelia, каждые
  15 минут; перенос legacy `avtovokzal57/refund.php`): деньги списаны, билетов
  нет, покупатель не вернулся. Билеты за него **не оформляем** — он мог об
  этой покупке и не знать; просто возвращаем деньги. **ЛОВУШКА:** отмена
  (`reverse`) работает только внутри операционного дня шлюза — оплата в 23:50
  и отмена в 00:50 уже не пройдёт, поэтому при отказе отмены делается полный
  возврат (`refund`); он идёт дольше и виден покупателю отдельной операцией,
  поэтому именно аварийный. Не вышло ни то, ни другое — заказ НЕ трогаем
  (деньги остаются у нас, решать человеку) и пишем на support, как делала
  `failnotify` в legacy. Сроки — `config/orders.php`
  (`ORDER_ABANDON_AFTER_MINUTES`, по умолчанию час; legacy ждал 40 минут).
  **Отказ от заказа** (`POST orders/{id}/cancel`): снимает бронь мест и
  отменяет регистрацию платежа. Бронь снимает sales-api
  (`DELETE reservations/{id}` → `KS_ABO_BRONTIME_PLACES`) — процедура убирает
  TimeMark и работает только для того агента, кто бронь ставил. Оплаченный
  заказ так отменить нельзя: деньги уже у нас, его либо дооформляют, либо
  возвращают. Статус шлюза при отмене важнее нашего — деньги могли списаться
  минуту назад, а возврата со шлюза мы ещё не видели.
  **ЛОВУШКА `SBERBANK_API_URI`: только схема и хост, без пути.** SDK сам
  приклеивает префикс (`Client::API_PREFIX_DEFAULT = '/payment/rest/'`,
  `Client::execute()`: `$uri = $apiUri . $action`), поэтому адрес с
  `/payment/rest/` на конце даёт `…/payment/rest//payment/rest/register.do`
  и шлюз отвечает **404** — заказ не создаётся, в логе `Bad HTTP code: 404`
  из `PaymentGateway->register`. Правильно: `https://3dsec-payments.yookassa.ru`
  (тест), `https://payments.yookassa.ru` (бой); у Сбера — `https://3dsec.sberbank.ru`
  и `https://securepayments.sberbank.ru`. Ловилось на проде 2026-11-14.
  Чек ККМ и письмо ставятся в database-очередь (`receipts`/`emails`):
  receipts обрабатывается через KKM API (воркер запускаем вручную:
  `queue:work --queue=receipts --stop-when-empty`), **воркер писем сознательно не запущен**.
  **Письма** — markdown-mailable (`app/Mail/*`, шаблоны
  `resources/views/mail/*.blade.php`): покупка (`PurchaseMail`, перенос
  legacy `emails/buy_success.php` + список билетов, код возврата и **PDF
  билетов вложением** — его рендерит тот же gotenberg по `/print/{id}`, и
  при его недоступности письмо уходит без вложения), возврат (`RefundMail`,
  перенос текста `backbycode.php` + разбивка суммы и отдельная формулировка
  для `bank_failed`), сброс пароля, подтверждение e-mail, приглашение в
  кабинет, уведомление об обращении. Общая подпись — один partial
  (`mail/partials/signature`), контакты в нём из `config/site.php`
  (`company`/`brand`/`support_email`/`support_phone`, значения legacy
  `inc/config.php`). Шапка и подвал переопределены в
  `resources/views/vendor/mail/{html,text}/message.blade.php` (в
  vendor-версии там `config('app.name')` и английское «All rights
  reserved»), фирменные цвета — тема `mail/theme-avtovokzal.blade.php`
  (`config/mail.php` → `markdown.theme`; Markdown ищет тему как view
  `mail.<имя>`, поэтому публиковать все компоненты не нужно).
  **`app.timezone` = Europe/Moscow** — времена рейсов BUSTER wall-clock; на UTC дедлайны
  «за 30 минут» уезжают на +3 ч, не менять. **Вместе с ним обязателен
  `'timezone' => Europe/Moscow` у соединения pgsql** (`config/database.php`): Eloquent
  пишет даты строкой БЕЗ смещения, и сессия Postgres в UTC принимает московское время
  за UTC — все timestamptz уезжают на +3 ч (ловилось на времени прибытия в билете:
  01:30 следующих суток вместо 22:30). То же — у ais-api (оба соединения, включая
  read-only `site`: отчёты режут выборку по московским суткам), у sales-api и
  у kkm-api — **пояс Europe/Moscow у ВСЕХ четырёх приложений**, и в
  `config/app.php`, и у соединения pgsql.
- **`kkm-api/`** — KKM API (Laravel 13, порт :8087): прослойка к KkmServer для фискальных
  чеков, по образцу sales-api (Bearer-токен `config/clients.php` + IP whitelist, журнал
  `kkm.api_requests`). Таблица `receipts`: **external_id — ключ идемпотентности клиента**
  (повтор не пробивает второй чек), IdCommand — идемпотентность внутри KkmServer
  (перед повторной отправкой всегда GetRezult). ЛОВУШКА GetRezult: внешний Status —
  статус самого GetRezult, результат исходной команды вложен в `Rezult` со своим Status.
  Backend шлёт чеки с ключами `sale:{uuid}` / `refund:{uuid}`; суммы позиций чека обязаны
  сходиться с оплатой до копейки (в чеке возврата разница построчных округлений
  компенсируется последней позицией). Смена >24 ч (54-ФЗ) закрывается автоматически:
  при отказе ККТ сервис распознаёт истёкшую смену (текст ошибки или GetDataKKT
  SessionState=3), пробивает Z-отчёт CloseShift и повторяет чек; новая смена
  открывается первым же чеком. Плюс ночной Z-отчёт в 23:59 МСК: команда
  `kkm:close-shift`, запускает **ofelia** (сервис `scheduler` в compose,
  `docker/ofelia/config.ini`, job-exec в контейнер `avtovokzal-kkm-app`) —
  отдельный php-контейнер под schedule:work НЕ поднимаем.
- **Перенос истории сайта** (команда backend `php artisan legacy:import-site`,
  2026-08-14): старая база сайта (Firebird `site.fdb`) переезжает в Postgres —
  `ORDERS` → `orders` + `tickets`, `BACKS` → `refunds`, `USERS` → `users`
  (кабинеты добавлены 15.11.2026, до этого не переносились). Список рассылки
  (`EMAIL`) по решению заказчика **не переносим**.
  **Кабинеты переносятся только те, за которыми есть покупки**: из 99 085
  записей legacy заказы есть у ~84 тыс., остальные — пустые кабинеты. Адреса
  без «@» (опечатки при регистрации, среди них попытки инъекций) пропускаются
  и пишутся в `storage/logs/legacy-import-skipped.log` — логином такой адрес
  быть не может, код из письма отправить некуда.
  **Пароль переезжает в `users.legacy_password`** — это md5(соль + пароль),
  как хранил legacy; соль берётся из `LEGACY_SITE_PASSWORD_SALT`
  (`config/legacy_site.php`, значение — `$CONFIG['password_sol']` боевого
  `inc/config.php`; **в git не кладём**, пусто = вход прежним паролем
  выключен и перенос кабинетов отказывается работать). При первом успешном
  входе `AuthService::login` пересохраняет пароль в bcrypt, гасит
  legacy-хэш и помечает адрес подтверждённым (пароль покупатель получал
  письмом на него же). Открытый `USERS.PASSWORD_RAW` **в новую базу не
  попадает вовсе** — md5 от девятизначного числа (а такие пароли рассылал
  старый сайт: 98 605 из 99 085) подбирается мгновенно, и держать его
  дольше необходимого нельзя. `PASSWORD_RAW` не переносится и по второй
  причине: у ~13,5 тыс. кабинетов он УСТАРЕЛ — `newpass.php` обновлял
  только md5, и в legacy старый пароль продолжал пускать в кабинет
  (вход там сверял `password` ИЛИ `password_raw`). Эту дыру не переносим:
  сброс и смена пароля у нас гасят `legacy_password`.
  Телефон у кабинетов legacy заполнен всего в 19 записях; `name` там не
  было вовсе, `DATE_REG` → `created_at`. После переноса кабинетов команда
  связывает заказы (`orders.user_id`) пачками по диапазону id — одним
  UPDATE это миллион строк в одной транзакции.
  Ключ `--only=users` переносит только кабинеты (к `orders`/`refunds` он
  тоже применим).
  **`orders.id` — varchar(36), а НЕ uuid**: legacy ORDER_ID (30 hex-символов)
  переносится как есть, поэтому старые ссылки и ключи продолжают работать, а
  новые заказы по-прежнему получают uuid (`HasUuids`). Того же типа `order_id`
  у `tickets`/`refunds`; маршруты вместо `whereUuid` используют
  `Order::ID_PATTERN`. Всё, чему нет места в новой схеме, лежит в jsonb
  `legacy`: у заказа — PLATNOM, NAPNAME, FRAHT, PRICES, STRAH/BAGAJ/BIL,
  SUMM_BACK, FP_BACK, CRONE, TIME_LIVE, COMMENT и исходный числовой STATUS;
  у билета — grj (гражданство строкой, до появления кодов), doc_orig,
  dobrstr/price_dobrstr (добровольное страхование, на новом сайте его нет);
  у возврата — WHO_BACK, TYPE_BACK, построчные суммы. **Маппинг статусов:**
  -4 → pending, 4 → payment_registered, 40 → paid, 1/5/6 → completed
  (5 и 6 — оформленные и позже возвращённые: сам возврат живёт в `refunds`),
  2/-1/-3 → failed, 3/-2 → cancelled. `PERSENT` в BACKS заполнялся не всегда —
  процент удержания тогда считается из сумм. Повторный запуск не плодит дубли
  (`insertOrIgnore` по legacy-идентификатору), чистый прогон — `--fresh`;
  есть `--since`, `--limit`, `--only`, `--chunk`. Реквизиты старой базы —
  `config/legacy_site.php` (по умолчанию контейнер firebird, база `site`),
  только на чтение.
- **`frontend/`** — Nuxt 4 + **Nuxt UI 4**: страницы `/` (поиск + hero bus.jpg + логотип из
  legacy), `/trips` (**объединяет legacy-поиск билетов и legacy-расписание до
  остановки**: переключатель `?all=1` показывает рейсы без интернет-продажи со
  статусами legacy — «Продажа в кассах», «Транзитный», «Нет свободных мест»,
  «Отменён», «Сорван», «Ушёл», «Продажа ограничена … не ближе/не дальше чем до»;
  без `?date` — режим «ближайшие», legacy `blij=1`),
  **`/buy?awtcod=&to=&date=&napcod=&raicecod=`** (рейс задан адресом, а не

- **Версия сайта для людей с нарушениями зрения** (ГОСТ Р 52872-2019, WCAG 2.1 AA;
  в legacy её не было — переносить было нечего): кнопка «Для слабовидящих» в
  шапке (`AccessibilityToggle.vue`) включает режим, настройки — в полосе над
  шапкой (`AccessibilityPanel.vue`), по умолчанию **свёрнутой**: включение
  режима не должно отодвигать страницу вниз экраном настроек. Состав —
  размер шрифта (3 шага), цветовая схема (три обязательные по ГОСТ: чёрным на
  белом, белым на чёрном, тёмно-синим на голубом, плюс коричневым на бежевом),
  изображения вкл/выкл, кернинг, межстрочный интервал, шрифт с засечками,
  «Обычная версия сайта» и сброс. Выключается целиком одной переменной:
  **`ACCESSIBILITY_VERSION=0`** в корневом `.env` (compose →
  `NUXT_PUBLIC_ACCESSIBILITY`), тогда нет ни кнопки, ни панели, ни класса на
  `<html>`.
  **Устройство — одно и главное: обычный режим не затрагивается.** Настройки
  (`useAccessibility.ts`) превращаются в классы на `<html>` (`a11y`,
  `a11y-scheme-*`, `a11y-font-*`…), и ВСЕ правила режима лежат в отдельном
  `app/assets/css/accessibility.css`, где каждый селектор начинается с
  `html.a11y`. Пока режим выключен, класса нет — ни одно правило не применяется.
  Состояние — в **cookie** `a11y`, а не в localStorage: класс нужен уже в
  SSR-разметке, иначе страница сначала показалась бы обычной и только потом
  перекрасилась. Cookie читается как чужие данные (`sanitize`).
  **Перекраска — двумя цветами схемы.** Обычная поверхность (страница,
  карточки, поля, выпадающие списки) — фон схемы и рамка цветом текста;
  акцентная (шапка, подвал, сплошные кнопки, выбранные пункты) — **инверсия**.
  Фон у блоков именно МЕНЯЕТСЯ: первая версия снимала его в прозрачный, и
  шапка с кнопками сливались со страницей — выглядело как сломанная вёрстка.
  **Ловушки, уже учтённые (не сломать при правках):**
  - `transform` НЕ сбрасываем — на нём держится позиционирование выпадающих
    списков и центрирование модалок (иначе все всплывающие слои собираются в
    левом верхнем углу).
  - `box-shadow` НЕ сбрасываем — на нём в теме Nuxt UI держатся рамки `ring-*`,
    то есть границы карточек, полей и панелей; снятие теней убирало границы
    блоков вместе с ними. Цвет им задают переопределённые `--ui-border` и др.
  - Иконки — это `<span class="iconify">` с `mask-image` и заливкой
    `currentColor`: фон схемы делает их невидимыми, заливку возвращаем отдельным
    правилом.
  - Правило по образцу `[class*="bg-error/"]` ловит `hover:bg-error/75` у
    СПЛОШНОЙ кнопки и ломает её инверсию — подпись пропадает (кнопка «Найти
    билеты» выходила чёрной на чёрном). Для полупрозрачных подложек отдельное
    правило не нужно: общий сброс и так красит их фоном страницы.
  - Декоративные накладки `absolute inset-0` (затемнение под заголовком
    главной, градиент под подписями плиток) остаются прозрачными — иначе
    закрыли бы и картинку, и текст.
  - Всплывающим слоям (`[role=dialog|menu|listbox]`,
    `[data-reka-popper-content-wrapper] > *`) фон ОБЯЗАТЕЛЕН.
  - Логотип `public/img/logo.png` — силуэт ЧИСТО БЕЛЫМ по прозрачному фону,
    поэтому на схеме «белым на чёрном» (полоса шапки становится белой) он
    инвертируется (`html.a11y-scheme-black header img`).
  - `<iframe>`/`<svg>` при выключенных картинках не прячем — в кадре капча
    формы обратной связи.
  - В самой панели свои интервалы (`letter-spacing: normal`,
    `line-height: 1.3`), кнопки панели не сжимаются (`flex: none`): с общими
    интервалами кружок-образец цвета вылезал за край своей кнопки, а общее
    `min-width: 0` позволяло флексу ужать кнопку уже её собственной подписи.
  - **`height: auto` у кнопок ломает КВАДРАТНЫЕ контролы.** Чекбокс, радио и
    переключатель в теме — это `<button role="checkbox">` с фиксированным
    `size-*`; «высота по содержимому» схлопывала их в полоску 21×4px (галочку
    «Я даю согласие…» было не видно и не во что нажать). Они исключены из
    правила через `:not([role=...])`, их размеры в `rem` и так растут с кеглем.
  - **`height: auto` у картинок ломает `object-cover`.** Снимок плитки
    «Популярные направления» (`absolute inset-0 w-full h-full object-cover`)
    получал натуральную высоту, не влезал в плитку и обрезался произвольным
    куском. У картинок задаём только `max-width`. Сама плитка перевёрстана:
    снимок **не увеличивается** (`width: auto`, потолок 400px у плитки и
    260px по высоте снимка — в пикселях, по размеру самих файлов 277–673px,
    а не в `rem`), подпись под ним. Растянутый на весь экран снимок 347px —
    мутное пятно, в котором слабовидящему всё равно нечего разобрать.
  - **Одной колонки мало, пока жив `col-span-*`.** Элемент на две колонки при
    единственной явной заставляет сетку создать НЕЯВНУЮ вторую размером
    `auto`: колонка настроек схлопывалась до 6px, и образец размера шрифта не
    помещался в кнопку. Поэтому рядом с `grid-template-columns: 1fr` стоит
    `grid-column: auto`. Исключений из «одной колонки» два, обоим колонки
    возвращены медиазапросами: панель настроек (в один столбец семь групп
    занимают пол-экрана) и плитки направлений (каждая не шире 400px, и в
    одну колонку они дали бы длинный столбец с пустым полем справа).
  - **Шапка не переносится — но только до `xl`.** Общий `flex-wrap` уносил
    кнопку меню на вторую строку, и шапка съедала треть экрана телефона. Ряд
    шапки — `nowrap`, кнопка меню всегда в правом углу, переносится НАЗВАНИЕ,
    логотип ниже 640px скрыт. Выше `xl` запрет снят: там не «бургер», а меню
    из пяти пунктов, и `nowrap` сжимал название до ширины колонки —
    «Орелавтотранс» разрывалось посреди слова. Граница та же, что у обычной
    шапки (меню из пунктов появляется с 1280px). Строка с галочкой тоже `nowrap`: иначе квадратик оставался
    один на строке, а подпись уезжала под него.
  - Тонкие разделители (`h-px bg-default` вокруг «или») общий сброс красил
    фоном страницы, и они пропадали — им отдельно возвращается цвет текста.
  **Вёрстка в режиме перестраивается, горизонтальной прокрутки быть не должно**
  (WCAG 1.4.10): ряды переносятся (`flex-wrap`, кроме `flex-col` и кроме рядов
  ВНУТРИ кнопок — там перенос означал бы «стрелка списка уехала под текст»),
  многоколоночные сетки становятся одной колонкой, `truncate`/`whitespace-nowrap`
  отменяются (не влезло — переносим, а не прячем за многоточием), фиксированные
  `min-w-*` обнуляются, у кнопок высота по содержимому. Размер шрифта задаётся
  КОРНЮ (вместе с текстом пропорционально растут rem-отступы), а **на экранах
  уже 480px шаги мельче** (17/20/22 вместо 18/22/26): на 320px при 26px от
  ширины экрана на текст не остаётся ничего.
  Проверка — прогон вёрстки по всем публичным страницам в iframe заданной
  ширины: ищется переполнение страницы, элементы за краем экрана, обрезанный
  многоточием текст и кнопки, у которых содержимое больше их самих. Прогнано на
  320/360/390/414/768/1024/1280/1440 во всех схемах и шагах шрифта, и в обычном
  режиме для сравнения. Тем же прогоном найдены и исправлены два дефекта
  ОБЫЧНОГО режима на 320px: кнопка «Перейти к оплате» уезжала за край экрана
  (`buy.vue`, не хватало `flex-wrap`) и таблица реквизитов растягивала страницу
  до 372px (`contacts.vue`, не было обёртки с прокруткой).
  Печатные формы (`/print/{id}`, `layout: false`) режима не знают, и в
  `@media print` он отключается принудительно: лист всегда чёрным по белому.
- **PWA: приложение на телефоне и купленные билеты без интернета**
  (в legacy ничего подобного не было — переносить было нечего). Сайт
  ставится на домашний экран (`public/manifest.webmanifest`, иконки
  `public/icons/`), а **купленные билеты открываются без сети** — ради
  этого всё и сделано: в автобусе связи может не быть, а билет показать
  надо.
  **Стартовый экран приложения — `/app`** (`start_url` манифеста), а НЕ
  главная: главная про одно действие (поиск рейса) и наполовину занята
  картинкой с формой, тогда как приложение открывают и ради билета в
  дороге, и ради телефона автовокзала. На экране четыре плитки —
  «Новости» (`/news`), «Покупка билета» (`/`), «Мои билеты»
  (`/tickets`), «Контакты» (`/contacts`) — плюс расписание и возврат
  билета. Разделы, которым нужна сеть, **без неё помечены «Нужен
  интернет»** и не кликаются: иначе покупатель тыкал бы в плитку и
  получал страницу «нет подключения». В приложении (`display-mode:
  standalone`) логотип в шапке ведёт на `/app`, а не на главную, и в
  мобильном меню появляется пункт «Главный экран» — иначе со стартового
  экрана не было бы дороги обратно.
  Плитка «Новости» ведёт в настоящий раздел — см. «Новости и объявления».
  **Предложение войти в кабинет** (`AppLoginPrompt` на `/app`): карточка
  на экране висит постоянно, окно показывается **не чаще раза в неделю**
  (отметка в `localStorage`) и только при сети — без неё войти всё равно
  нельзя, а место на экране оно займёт. Срок жизни самой авторизации не
  трогали: полгода бездействия, продлеваемые при каждом заходе (и
  cookie, и `last_used_at` токена) — тот, кто открывает приложение хотя
  бы раз в полгода, не разлогинится никогда.
  **Данные билетов — IndexedDB, а не кэш service worker**
  (`app/composables/useOfflineTickets.ts`, база `avtovokzal-offline`):
  кладётся ответ `GET /orders/{id}/print` — тот же, из которого рисуется
  печатная форма и PDF. Ответы API в Cache Storage не попадают вовсе: они
  ходят с Bearer-токеном кабинета, а в билете лежат ФИО и номер
  документа. Сохраняется билет **сразу после оформления** (страница
  `/payment/result`, в том числе гостю — кабинета у него нет) и при
  заходе в кабинет (`/lk` подтягивает предстоящие поездки, они же
  обновляются при открытии `/tickets`). Чистится само: через сутки после
  отправления рейса, через 30 дней от сохранения (дальше backend всё
  равно обезличивает), **и целиком при выходе из кабинета** —
  но именно в `logout()`, а НЕ в `forgetSession()`: вторая срабатывает и
  когда `/auth/me` не ответил из-за сети, то есть билеты стирались бы
  ровно тогда, когда нужны.
  **Service worker (`public/sw.js`) написан руками**, без workbox и
  `@vite-pwa/nuxt`: нужны три стратегии, а сборочный precache-манифест
  плохо ложится на SSR (оболочку отдаёт Nitro, а не статический
  index.html). Он кэширует оболочки `/app`, `/tickets` и `/offline` (все
  `ssr: false` в `nuxt.config.ts` — иначе в кэш попала бы SSR-разметка с
  чужими персональными данными), статику `_nuxt/*` и картинки
  (cache-first, имена с хэшем), а навигации ведёт network-first с
  откатом на `/offline`. **VERSION в файле поднимается руками** — по ней
  чистятся старые кэши.
  **`/contacts` — единственная СЕРВЕРНАЯ страница в кэше** (её читают
  поисковики, `ssr: false` ей нельзя): в кэш ложится готовая разметка с
  адресами и телефонами, поэтому без сети она открывается вообще без
  запросов — данные уже внутри HTML. Из личного там только e-mail в
  шапке, и при выходе из кабинета кэш оболочек стирается целиком
  (сообщение `CLEAR_SHELL`, `clearOfflineShell()`).
  **Ловушки, уже учтённые (не сломать при правках):**
  - **Регистрацию нельзя вешать только на `window.onload`.** Страницы
    `/tickets` и `/offline` рендерятся в браузере, их гидрация идёт ПОСЛЕ
    загрузки документа — событие уже прошло, и service worker не
    регистрировался ровно там, где он нужен. В плагине
    (`plugins/pwa.client.ts`) проверяется `document.readyState`.
  - **Манифест отдаётся network-first, а не как остальная статика.**
    Лежал среди `_nuxt/*` и картинок (cache-first) — и браузер при
    установке читал СТАРУЮ копию: с прежним `start_url` и прежними
    настройками. Снаружи это выглядит как «приложение ставится не тем,
    чем должно». Ловилось 15.11.2026 при переезде `start_url` на `/app`.
  - **«Ставится ярлык, а не приложение» — обычно НЕ поломка сайта.** На
    Android удаление иконки с домашнего экрана не удаляет само
    приложение (WebAPK): оно остаётся в системе, Chrome считает его
    установленным и на повторную просьбу делает лишь ярлык. Проверять
    установимость надо не на глаз, а через CDP: `Page.getAppManifest`
    (`errors`) и `Page.getInstallabilityErrors` — оба пустые значат, что
    критерии выполнены. Приложение само спрашивает браузер, не стоит ли
    оно уже (`detectInstalledApp` → `getInstalledRelatedApps`, для чего
    манифест ссылается сам на себя в `related_applications`), и тогда
    прячет свои кнопки установки; в инструкции (`InstallAppDialog`)
    описано, как удалить приложение по-настоящему.
  - **`cache.add()` не годится для precache:** любой не-2xx ответ рушит
    всю пачку целиком и молча. Кэшируем `fetch` + `cache.put` поштучно,
    обязательно с `cache: 'reload'` — иначе в офлайн-копию ляжет разметка
    прошлой сборки со ссылками на скрипты, которых на сервере уже нет.
  - **Страницу билетов прогреваем заранее** (`warmOfflineShell`): после
    сохранения билета приложение шлёт service worker сообщение
    `CACHE_SHELL` и просит Nuxt подгрузить чанк `/tickets`. Иначе офлайн
    работал бы только у тех, кто хотя бы раз открывал эту страницу сам.
  - Запрос сессии (`/api/auth/session`) при открытии приложения **без
    сети падает** — в `useAuth.readSession` он обёрнут в try/catch, иначе
    плагин авторизации роняет всё приложение и билеты не показать.
  - Предложение установить приложение (`InstallAppPrompt`) показывается
    **не чаще раза в неделю** (отметка в `localStorage`), не на страницах
    покупки/оплаты/печати и уступает напоминанию о незавершённой покупке
    (общий флаг `usePendingNotice` — внизу экрана место одно, а там чужие
    деньги).
  - Кнопка «Установить приложение» в мобильном меню видна **всегда**
    (кроме уже установленного приложения): `beforeinstallprompt` не
    приходит ни в Safari, ни во встроенных браузерах соцсетей, и без
    инструкции (`InstallAppDialog`: Safari на iOS, Chrome на Android)
    покупатель просто не нашёл бы, где установка.
  Выключается целиком — **`PWA=0`** в корневом `.env` (compose →
  `NUXT_PUBLIC_PWA`): ни service worker, ни кнопок установки. В dev
  service worker не регистрируется в любом случае — его кэш мешает Vite
  отдавать свежие бандлы.
- **Личный кабинет покупателя** (перенос legacy `url/lk.php`, `login.php`,
  `register.php`, `forgot.php`, `newpass.php`, `change.php`, `ticketback.php`):
  backend `auth/*` + `cabinet/*`, фронт `/lk`, `/lk/profile`, `/login`,
  `/register`, `/forgot`, `/reset`. Авторизация — **Bearer-токен Sanctum**
  (им же будет ходить мобильное приложение). Токен хранится в **httpOnly
  cookie `av_session`, которую ставит сервер Nuxt** (`frontend/server/api/auth/
  session.{get,post,delete}.ts`): cookie и localStorage, записанные из JS,
  Safari/ITP стирает через ~неделю — покупатель разлогинивался бы. Портал
  получает токен из `GET /api/auth/session` (SSR — с cookie запроса) и шлёт
  в backend как Bearer. Менять cookie можно только same-origin запросом
  (`assertSameOrigin`) — иначе чужой сайт подсунул бы свой токен.
  **Срок — полгода бездействия с обеих сторон:** `maxAge` cookie обновляется
  при каждом чтении сессии, а токен проверяется по `last_used_at`
  (`Sanctum::authenticateAccessTokensUsing` в AppServiceProvider,
  `site.token_idle_minutes`; `expiration` Sanctum не годится — он считает
  от created_at). Мёртвые токены и старые ссылки писем чистит
  `auth:prune-tokens` (ofelia, ежедневно в 04:30).
  Схема сразу под расширение (вход по SMS): способы входа —
  строки `user_identities` (`password` | `vk` | `phone`), пароль в `users`
  **nullable**. Ссылка-приглашение в кабинет (после первой покупки) — в
  `auth_tokens` (в базе только sha256, TTL, отметка использования); legacy
  хранил пароль открытым текстом в `USERS.PASSWORD_RAW` — **не повторять**.
  Пароль: `trim` при задании И при проверке, минимум 8 символов, сложность
  сознательно не проверяем. У кабинета, переехавшего со старого сайта,
  пароль лежит в `legacy_password` (см. «Перенос истории сайта»), поэтому
  «есть ли пароль» спрашиваем через `User::hasPassword()`, а НЕ по
  `users.password` — иначе профиль предлагал бы «Задать пароль» тому, у
  кого он есть, а смена пароля не спрашивала бы текущий.
  Поля пароля на сайте — `PasswordInput.vue`
  («глазок»): с телефона опечатку в скрытом поле не видно, и человек не
  понимает, почему «пароли не совпадают». Заказы кабинета ищутся по `user_id` **или**
  `orders.email` — покупки «на этот e-mail» до регистрации считаются своими.
  У авторизованного покупателя e-mail заказа берётся из профиля (поле на форме
  покупки заблокировано), телефон редактируется. Письма кабинета
  (код подтверждения, сброс пароля) шлются **синхронно**, приглашение после
  первой покупки — джобом в очередь `emails` (воркер писем по-прежнему не
  запущен).
- **Подтверждение e-mail кодом из письма (6 цифр)** — таблица **`auth_codes`**,
  сервис `AuthCodeService`, лимиты в `config/site.php` → `auth_code`
  (сделано 15.11.2026). До этого регистрация **вообще не подтверждала
  адрес**: кабинет открывался сразу, а по `orders.email` ему видны покупки,
  сделанные на этот адрес до регистрации — то есть на чужой адрес можно
  было завести кабинет и увидеть чужие билеты с ФИО и документами. В legacy
  такой дыры не было: там пароль не задавался, а **генерировался и уходил
  письмом** (`url/register.php`, ветка при `$CONFIG['reg_mode'] != 'code'`).
  Правила кода: живёт **30 минут**, **5 попыток** ввода на пару «адрес +
  код» (счётчик в БД — требование «неважно с какого браузера»), повторная
  отправка **не чаще 3 минут**, **не более 5 кодов на адрес в сутки**
  (отдельно по каждому процессу: общий потолок закрыл бы восстановление
  пароля тому, кто перед этим не смог зарегистрироваться). Исчерпали
  попытки — код гасится (`blocked_at`), нужен новый. В базе **bcrypt**
  кода, а не sha256: у шестизначного кода всего миллион значений.
  **Пользователь при регистрации создаётся ТОЛЬКО после кода** — данные
  (хэш пароля и телефон) ждут в `auth_codes.payload`, иначе неподтверждённый
  кабинет занимал бы чужой адрес. Три процесса на кодах: регистрация
  (`POST auth/register` → `auth/register/confirm`), восстановление пароля
  (`auth/password/forgot` → `auth/password/reset` с `email`+`code`), добавление
  e-mail кабинету из VK (`auth/email` → `auth/email/confirm`, уже под
  `auth:sanctum` — привязать адрес можно только своему кабинету).
  Повторная отправка — `auth/code/resend`. **ЛОВУШКА лимита запросов:**
  маршруты ввода кода вынесены в `throttle:30,1` — на общих `throttle:10,1`
  человек, пару раз ошибившийся цифрой, получал «Too Many Attempts» вместо
  подсказки; само по себе это не ослабление, перебор закрывают 5 попыток в
  БД. Английский текст 429 тоже убран — `ThrottleRequestsException`
  рендерится по-русски в `bootstrap/app.php`.
  Фронт: `AuthCodeForm.vue` (UPinInput на 6 цифр, автоотправка по последней
  цифре, отсчёты **из ответа сервера** — своих констант фронт не держит,
  иначе «отправить снова» включалось бы раньше, чем сервер готов).
  Страницы `/reset` и `/confirm-email` остались **редиректами** на `/forgot`
  и `/lk/profile` — ради писем, отправленных до перехода.
- **В письмах сайта НЕТ ссылок** — ни в шапке, ни в подвале, ни в тексте
  (решение заказчика 15.11.2026: из-за ссылок письма уходили в спам).
  Поэтому: свой `resources/views/vendor/mail/html/header.blade.php` без
  `<a href>`, подпись без `mailto:`, в письме о покупке вместо кнопки
  «Открыть билеты» — **то же вложением PDF**, приглашение в кабинет без
  ссылки и без токена (владение адресом теперь доказывает код регистрации).
  Письмо с кодом (`AuthCodeMail`) markdown-шаблон `mail::message` не
  использует вовсе — у него свой blade без шапки и подвала.
  **Проверка:** отрендерить все mailable и убедиться, что нет ни `href`,
  ни `http://` в тексте (скрипт разового прогона — в истории коммита
  «Подтверждение e-mail кодом»). Автолинковка Markdown не мешает:
  `Illuminate\Mail\Markdown` подключает только CommonMarkCore и Table,
  без GFM-autolink, поэтому адрес почты остаётся текстом.
- **Вход через VK ID** (в legacy входа через соцсети не было — новая
  возможность): OAuth 2.1 + PKCE **без JS-SDK**. Кнопка — обычная ссылка на
  серверный маршрут Nuxt `/auth/vk`, тот спрашивает у backend адрес
  авторизации (`auth/vk/start`, там же генерируются code_verifier и state) и
  уводит на `id.vk.ru/authorize`; возврат ловит `/auth/vk/callback`, код на
  токен меняет backend (`auth/vk/callback` → `VkIdClient`), а Nuxt кладёт
  выданный Sanctum-токен в ту же httpOnly cookie `av_session`. client_id и
  обмен кода фронту не видны. **state одноразовый**: verifier лежит в кэше
  backend (сессии у API нет) и вынимается через `Cache::pull`, плюс дубль
  в httpOnly cookie `vk_state` — сверка защищает от подсунутого чужого кода.
  Токен VK после получения профиля гасим (`/oauth2/logout`) — ходить в VK
  от имени покупателя мы не собираемся. Ключи — `VK_CLIENT_ID` /
  `VK_CLIENT_SECRET` (`config/vk.php`); **пустой client_id = вход выключен**,
  кнопки нет (тестовых приложений VK не выдаёт, как и у SmartCaptcha).
  Адрес возврата собирается ТОЛЬКО из конфига (`VK_REDIRECT_URI`, иначе
  `FRONTEND_URL`), а не из запроса: он обязан совпадать байт в байт в
  настройках приложения VK, в `/authorize` и в `/oauth2/auth`.
  **VK принимает только https и только стандартный порт**, поэтому на
  локальном контуре поднят https-вход: сервис `proxy` (Caddy,
  `docker/caddy/Caddyfile`, порт **443**, самоподписанный `tls internal`),
  сайт открывается как **https://avtovokzal57.local** — имя прописано в
  `/etc/hosts` (127.0.0.1). Он отдаёт под
  ОДНИМ origin и сайт, и `/api/v1/*` — со страницы по https браузер не даст
  обратиться к http-API (mixed content); `useApi` это учитывает
  (`browserApiBase`: при https-странице базой становится origin). Только
  `/api/v1/*`, потому что `/api/auth/session` — собственный маршрут Nuxt.
  В Caddyfile имена сайта заданы явно (`avtovokzal57.local`, `localhost`,
  `127.0.0.1`): для безымянного блока `tls internal` не может выпустить
  сертификат и рвёт рукопожатие. `VK_REDIRECT_URI` на локальном контуре
  указывает на это имя, http://127.0.0.1:3000 продолжает работать как раньше.
  **Кнопка ведёт ПРЯМО на `id.vk.ru`**, а не на наш `/auth/vk`: такую ссылку
  телефон отдаёт приложению VK (Android App Links / iOS Universal Links), и
  вход происходит в один тап. Через `/auth/vk` этого не было — там
  302-редирект, а на редиректах система ссылку приложению не передаёт и
  открывает веб-форму. Адрес кнопка получает заранее у серверного маршрута
  `/api/auth/vk/start` (он же кладёт `vk_state` в cookie); пока ответа нет
  и при выключенном JS в `href` остаётся прежний `/auth/vk`.
  **E-mail от VK может не прийти** (нет у аккаунта или не дали доступ) —
  по решению заказчика такой кабинет заводится всё равно: `users.email`
  **nullable**, почту потом *предлагаем* (страница профиля, редирект
  `/lk/profile?add-email=1` сразу после первого входа), но не требуем.
  **Покупать без почты тоже можно:** на форме покупки поле необязательно для
  авторизованного (гостю по-прежнему обязательно), а в заказ уходит
  служебный адрес `site.fiscal_fallback_email` (`FISCAL_FALLBACK_EMAIL`).
  Он нужен фискальному чеку — по 54-ФЗ электронный чек надо куда-то
  отправить, и пустой адрес ККТ не примет. **НАШИ письма на этот адрес не
  идут** (билеты, приглашение в кабинет, уведомление о возврате — проверка
  `OrderService::isFiscalFallbackEmail`), и по нему же не ищутся заказы
  кабинета: ящик общий, иначе по нему сошлись бы покупки разных людей.
  Записать введённый адрес сразу нельзя — кабинет показывает покупки по
  `orders.email`, поэтому владение подтверждается **кодом из письма**
  (`auth_codes` type=`email_confirm`, ввод прямо в профиле); адрес,
  пришедший от VK, считается подтверждённым сразу. Если e-mail от VK совпал
  с существующим кабинетом — VK **привязывается к нему** (второго кабинета
  с теми же покупками не заводим). У кабинета без пароля профиль показывает
  «Задать пароль» (логином будет e-mail, поэтому без адреса пароль задать
  нельзя), а форма покупки не блокирует поле e-mail — брать его неоткуда.
  **Телефон в профиле необязателен** (`PUT auth/profile`, пустое значение
  стирает номер): кабинет из VK может остаться вообще без контактов. При
  регистрации по e-mail и в форме покупки номер по-прежнему обязателен.
  **«Войти через VK» — всегда первым пунктом** (страницы входа и
  регистрации, модалка на `/buy`, предложение в приложении): это вход в
  один тап, без пароля и без кода из письма, а под формой кнопку просто
  не замечали.
  На `/buy` гостю предлагается войти или зарегистрироваться (модалка;
  ссылки несут `?redirect=` на текущий рейс, там же кнопка VK, `/register`
  этот параметр понимает). Шаг **необязательный**, и отказ НЕ запоминается —
  предложение показывается при каждой покупке: решение завести кабинет
  созревает не с первого билета, а увиденное один раз окно больше не
  вернётся. При недоступном к покупке рейсе не показывается вовсе.

  упрощениях): backend `POST /api/v1/admin/refunds/inspect|confirm|repair` +
  страница ais-spa `/back-ticket` (vite-proxy `/site-api` → web). Отличия от
  возврата по коду: без дедлайна и после отправления рейса (`admin_mode` в
  sales-api /refunds пропускает проверку IS_PRN — как legacy), сверка оплаты
  `getOrderStatusExtended` до возврата, процент удержаний выбирает админ
  (0/5/15/25 + рекомендуемый от станции; на вендорную ведомость процент НЕ
  влияет — в legacy `shtraf` до KS_ANN_TICKET_FROM_AW не доходил), починка
  зависшего возврата денег. Формула суммы — как в back_bilet (number_format,
  округление round), НЕ как в backbycode (floor). Права сотрудника:
  `back-ticket.inspect` на поиск билета, `back-ticket.refund` и
  `back-ticket.repair` — с кодом подтверждения.
- **`ais-spa/`** — SPA отчётов АИС (Vue 3 + Vite, :3001 dev): перенос из устаревшего
  репозитория `avtovokzal_ais_spa` (тот был под legacy apiv2). `/api` → ais_web через
  vite-proxy.
- **Сотрудники АИС, роли и права** (в legacy авторизации не было вовсе —
  доступ закрывало ограничение по IP на nginx, и внутри сети отчёты и
  возврат билета открывал кто угодно с любой машины; переносить было
  нечего). Сотрудники, роли и сессии живут в **БД `ais`** (ais-api):
  таблицы `employees`, `roles`, `employee_role`, `employee_tokens`.
  - **Каталог модулей и прав — `shared/ais_permissions.php`** (как
    `shared/stations.php`): `config/ais_modules.php` обоих приложений
    делает `return require`. Ключ права — `<модуль>.<право>`
    (`pages.edit`, `back-ticket.refund`). Набор прав у модулей РАЗНЫЙ.
    Отчёты в каталоге НЕ перечислены: их модуль `report:<slug>` АИС
    собирает на лету из `config/reports.php` (`ModuleRegistry`), иначе
    список отчётов жил бы в двух местах. Новый отчёт появляется в
    редакторе ролей сам.
  - **Опасные права помечены в каталоге (`confirm`)**, а не в маршрутах:
    сервер отвечает 428 `need_confirm`, клиент спрашивает личный код
    сотрудника и повторяет запрос с заголовком `X-Confirm-Code`. Так
    список опасных операций не расходится с тем, что видит администратор
    в редакторе ролей.
  - **Роль «Администратор» системная** (`roles.is_system`): права не
    хранит и не редактируется — ей доступно всё, включая модули, которых
    ещё нет. Её создаёт МИГРАЦИЯ, а не сид: без неё первый `ais:admin`
    остался бы без роли.
  - **Первый администратор — `php artisan ais:admin <логин>`** (ais-api).
    Ею же сбрасывают пароль, когда он потерян; дальше сотрудников
    создаёт и сбрасывает любой администратор в АИС. Без `--password`
    пароль генерируется парольной фразой и печатается.
  - **Логин** нечувствителен к регистру и к пробелам по краям, состав
    символов НЕ ограничен (русские буквы можно): `login` как ввели +
    `login_normalized` для поиска (`App\Support\AisLogin`).
  - **Надёжность пароля — zxcvbn** (`bjeavons/zxcvbn-php`, перенос модуля
    из проекта `api.gotov.org`): считается стойкость к подбору, а не
    состав символов, поэтому фраза из слов одного регистра проходит, а
    «Пароль123!» нет. Плюс русский словарь (`RussianPasswordDictionary`)
    и проверка обеих раскладок (`gfhjkm` = «пароль»). `trim` и при
    установке, и при проверке. Длина и порог — `shared/ais_auth.php`.
  - **Три секрета у сотрудника, у каждого своя роль:** `password`
    (bcrypt), `confirm_code` — код подтверждения опасных действий
    (bcrypt, 3–20 любых знаков, никому не показываем), `fast_token` —
    токен быстрого входа по ссылке `?token=…`. Токен обязан
    ПОКАЗЫВАТЬСЯ владельцу, поэтому лежит в шифре Laravel, а искать по
    нему позволяет отдельный sha256 (`fast_token_hash`): Crypt у каждого
    шифрования даёт разный результат, индексом по нему не найти.
  - **Токен быстрого входа действует ТОЛЬКО из доверенных сетей**
    (`ais_auth.token_networks`, по умолчанию приватные диапазоны): он
    виден в адресной строке, в истории браузера и в журналах прокси.
    Пустой список = вход по токену выключен. SPA, увидев `?token=`,
    обменивает его на обычную сессию и СРАЗУ убирает из адреса — причём
    до монтирования приложения, иначе vue-router затирает наш
    `replaceState` и токен остаётся в истории.
  - **Сессия — своя таблица `employee_tokens`, не Sanctum:** её читает и
    backend (см. ниже), а хэш считается тем же sha256 без секрета
    приложения — иначе приложениям пришлось бы делить APP_KEY.
    **Токен несёт httpOnly-cookie `ais_session`, её ставит сервер:**
    сессия живёт месяцами (`session_idle_minutes` 90 дней, предельного
    срока нет), а localStorage и cookie из JS Safari/ITP стирает примерно
    через неделю — сотрудник разлогинивался бы сам (та же причина, что у
    кабинета сайта). `SameSite=Lax` закрывает CSRF. Мёртвые строки чистит
    `ais:prune-tokens` (ofelia, 04:35).
  - **`trustProxies(at: '*')` в ais-api обязателен:** без него
    `$request->ip()` равен адресу docker-сети, и проверка «из рабочей
    сети» либо не работает вовсе, либо разрешает кого угодно.
  - **Админские маршруты backend (`/api/v1/admin/*`) защищены тем же
    сотрудником**: middleware `ais.can:<право>` (`App\Services\AisAuth`)
    читает `employees`/`roles`/`employee_tokens` ПРЯМЫМ запросом в БД
    `ais` (соединение `ais` в `config/database.php`), а не по сети у
    ais-api: админку и backend открывают с одного домена, cookie приходит
    и туда, а лишний вызов с кэшем прав на каждый запрос не нужен.
    В эту базу backend пишет единственное — отметку обращения к сессии.
    `?token=` там сознательно НЕ принимается: токен в адресе осел бы в
    журналах nginx рядом с правом на возврат денег.
  - **Права проверяет только сервер.** Фронт по ним лишь скрывает пункты
    меню и кнопки (список отчётов приходит уже отфильтрованным —
    отчёта, которого нет в меню, для сотрудника не существует). Проверять
    в двух местах значит расходиться с сервером при первой правке роли.
  - **Нельзя остаться без администратора:** себя не отключить и не
    удалить, с себя не снять роль администратора, последнего активного
    администратора не разжаловать — иначе оставался бы только
    `ais:admin` на сервере.
  - Страницы ais-spa: `/login` (экран-гейт вместо приложения),
    `/profile` (свой пароль, код и токен), `/employees`, `/roles`.

### Валидация данных пассажира (не ослаблять!)
- **Дата рождения: не старше 100 лет и строго в прошлом.** Правило вендорной
  процедуры `KS_CONTROL_BIRTH_PAS`: `birth_day >= Current_Date - 100 лет` И
  `birth_day < Current_Date`. Проверяется ДО оплаты (`StoreOrderRequest`,
  `SavePassengerRequest`, `DateInput` на фронте) — раньше стояло
  `after:1900-01-01`, и дата вроде 12.12.1922 ловила отказ станции «Дата
  рождения … указана неверно» уже на оформлении, когда деньги списаны.
- Правила серии/номера документа сняты 1:1 с вендорной процедуры
  **`KS_CONTROL_DATA_PAS`** (исходник — `docs/buster-procedures/`) и выполняются
  ДО оплаты: `backend/app/Services/PassengerDocument.php` + `StoreOrderRequest::after`.
  При изменениях сверять скриптом (18 кейсов против живой процедуры — см. историю
  коммита «Валидация документов по правилам станции»).
- ФИО: BUSTER не проверяет и молча режет до 20/14/14 — лимиты и фильтр символов
  (буквы/дефис/пробел/апостроф) держим на backend. **Ё всегда заменяется на Е**
  (`OrderService::normalizeName`) — буква Ё ломает вендорный софт станции.
- Справочник гражданств — таблица `citizenships` (коды COUNTRIES_TABLE, 185 = Россия),
  сид `CitizenshipSeeder` из `database/data/citizenships.json`. В кэш класть только
  массивы: Eloquent Collection в database-кэше десериализуется в incomplete class.

### Legacy через ODBC-shim

Боевой код работает в контейнерах `legacy`/`legacy_site` **без правок**: класс `db_work`
написан под ODBC, а `docker/legacy/odbc-shim.php` (`auto_prepend_file`) эмулирует `odbc_*`
через нативный Firebird и перенаправляет все подключения на контейнер `firebird`.

**Ловушки shim, уже учтённые (не сломать при правках):**
- Явные транзакции: `ibase_trans` + `commitT` — без коммита INSERT/UPDATE не сохраняются
  (симптом: оплата прошла, а заказ «не оформлен»).
- TIMESTAMP теряет миллисекунды при биндинге ibase → таймстемпы **инлайнятся прямо в SQL**.
- `charSet` берётся из DSN (как боевой драйвер): конфиги с `charSet=UTF-8` отдают UTF-8,
  без — сырой WIN1251 (страница сама делает `iconv`).
- **Таймзоны:** Firebird и PHP должны быть в **+3** (`TZ=Europe/Moscow`), иначе payconfirm
  падает на сверке времени резерва.

## Базы

- **PostgreSQL** (`db`) — наши данные (`site`, `ais` после переноса), `./data/postgres`.
  **Сервер живёт в Europe/Moscow** (`command: postgres -c timezone=…` в compose,
  плюс `TZ` контейнера): `now()`, журнал и вывод timestamptz — в +3.
  **ЛОВУШКА:** Eloquent пишет даты строкой БЕЗ смещения, поэтому пояс СЕССИИ
  решает всё — каждое приложение задаёт его ЯВНО в своём `config/database.php`
  (все четыре — `Europe/Moscow`). Положись они на умолчание сервера, их
  timestamptz уехали бы на 3 часа при смене пояса сервера. Проверка:
  `show timezone` из каждого контейнера.
  **sales-api и kkm-api раньше жили в UTC — переведены на +3 15.11.2026.**
  У sales-api это не только про свои таблицы: он сравнивает времена рейсов
  BUSTER (московские wall-clock) обычными `date()`/`time()` — сегодняшняя
  дата в поиске рейсов и отсечка «не ближе 2000 секунд до отправления», —
  и в UTC эти сравнения уезжали на 3 часа: в список попадали уже ушедшие
  рейсы, а с полуночи до трёх ночи «сегодня» оказывалось вчерашним числом
  (купить их всё равно не давал фронт, у него своя отсечка).
  **ЛОВУШКА:** пояс процесса Laravel выставляет из `config('app.timezone')`
  (`date_default_timezone_set` в LoadConfiguration), поэтому `TZ`
  контейнера на `date()` НЕ влияет — менять надо конфиг, а не compose.
  Данные, записанные до перевода, остались в UTC: это тестовые прогоны,
  исправлять их не стали.
- **Firebird 2.5** (`./databases`, восстановлены из бэкапов): `BUSTER` (buster.fdb, Красная
  Заря, вендорная), `ais` (ais.fdb), `site` (site.fdb).
  Восстановление: `gbak -c -n -o -user SYSDBA -password masterkey <файл.fbk> /firebird/data/<имя>.fdb`
  (`-n` обходит NOT NULL в вендорных бэкапах).

isql к нашим базам:
```bash
docker compose exec -T firebird /usr/local/firebird/bin/isql -user SYSDBA -password masterkey site
```
