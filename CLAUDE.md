# CLAUDE.md — avtovokzal_new_platform

Инструкции для Claude Code по работе с этим репозиторием. Читай вместе с
[README.md](README.md), [PLAN.md](PLAN.md) и [docs/LEGACY.md](docs/LEGACY.md) — здесь только
то, что не выводится из кода: правила, ловушки и как что запускать.

## Что это

Модернизация АИС автовокзалов. Три легаси-компонента (сайт `avtovokzal57`, АИС `ais`,
API продаж `ais/api`) переводим на **PHP 8.5 / Laravel 13 / Nuxt / PostgreSQL 17** в Docker
Compose. Вендорные Firebird-базы продаж (BUSTER и др.) **не трогаем** — структура вендорная.
Идёт **этап переноса**: покупка, возврат по коду, печатные формы и фискализация уже
работают на новом стеке (сквозные прогоны 2026-08-03); статус по этапам — в PLAN.md.

## Правила (обязательно)

- **НЕ упрощать функциональность legacy при переносе без ЯВНОГО разрешения
  пользователя** и не делать допущений, не соответствующих реальности
  («аналог», «примерно то же») — изучить исходник целиком, найти все отличия
  и воспроизвести. Если кажется, что что-то можно упростить/выкинуть —
  сначала спросить. Явно разрешённые упрощения фиксировать здесь
  (разрешено: защитный код 123321 в back_bilet.php не переносим —
  позже будет нормальная авторизация; IP-ограничения агентов в legacy
  на локальном контуре убраны).
- **Боевой legacy-код правим ТОЛЬКО в локальной копии `./htdocs`** (распакованный бэкап).
  Никогда — на CIFS-шаре `/mnt/htdocs`.
- **На шаре `/mnt/htdocs` НЕ использовать `perl -i` / `sed -i`** — файл удаляется. Только
  прямая перезапись через Write. (См. память `cifs-no-inplace-edit`.)
- **Именованные тома Docker не используем** — только bind mounts (`./data`, `./htdocs`, …).
- **`dist/` и `data/postgres/` не коммитим** — это артефакты сборки/данные.
- **Тестовая покупка билета:** всегда с багажом, по 2–3 билета за раз. При неоднозначности —
  **остановиться и спросить** пользователя.
- Тестовые креды (SMB `admin/avtovokzal57`, шлюз Сбербанка `metagraphica/metagraphica`,
  тест-карта) — только для локальной разработки, наружу не публиковать.

## Окружение

```bash
docker compose up -d          # поднять стек
docker compose ps             # статус
docker compose logs -f <svc>  # логи
docker compose down           # остановить (данные Postgres в ./data сохранятся)
```

**Публичный адрес сайта — одна переменная `SITE_URL` в корневом `.env`.**
На проде это **`https://автовокзал57.рф`** (домен отдан новой платформе
15.11.2026; технический домен `site.orelavtotrans.ru` **отключён**
16.11.2026 по решению заказчика — посетителей у него не было, он был
временным адресом на время переноса). Адрес пишется
кириллицей — он попадает в билет (ссылка возврата по коду) и в SEO-разметку,
а punycode там читается как подделка. **Исключение — адреса, которые внешняя
система сверяет байт в байт:** `SBERBANK_RETURN_URL` и `VK_REDIRECT_URI` в
`backend/.env` задаются в punycode (`https://xn--57-6kcaja9axlzb9b.xn--p1ai/…`),
иначе шлюз и VK адрес не примут.
Compose раздаёт её сервисам (`docker-compose.yml`): `FRONTEND_URL` у `app`,
`SITE_FRONTEND_URL` у `ais_app`, `NUXT_PUBLIC_SITE_URL` у `frontend`,
`VITE_SITE_URL` у `ais_spa`; в проде то же значение идёт и в
`NUXT_PUBLIC_API_BASE` (API живёт на том же домене). Из `FRONTEND_URL`
выводятся адрес возврата платёжного шлюза (`services.sberbank.return_url`) и
`redirect_uri` VK — отдельные `SBERBANK_RETURN_URL` / `VK_REDIRECT_URI`
нужны только когда возврат должен идти на другой адрес. **Ловушка:**
переменная окружения контейнера перекрывает одноимённую строку в
`backend/.env` (Dotenv не перезаписывает уже заданные переменные) — правка
`FRONTEND_URL` в `backend/.env` на поднятом стеке ничего не изменит, менять
нужно `SITE_URL`. После правки — `docker compose up -d` (не `restart`:
окружение задаётся при создании контейнера).

**ЛОВУШКА 502 после `docker compose up -d`:** nginx в контейнерах
(`web`, `ais_web`, `sales_web`, `kkm_web`) резолвит имя php-fpm **один раз
при старте**, а `up -d` пересоздаёт php-контейнеры с новым IP — и сервис
начинает отвечать 502 «connect() failed», пока nginx не перезапустят.
Поэтому в `docker/nginx/*.conf` адрес подставляется переменной
(`set $php_upstream app:9000; fastcgi_pass $php_upstream;`) рядом с
`resolver 127.0.0.11` — тогда имя резолвится на каждый запрос. Ловилось на
проде 15.11.2026: после правки `.env` и пересоздания контейнеров АИС отдавал
502, хотя сам `ais_app` работал.

Порты: web :8088 (backend, высокоуровневое API avtovokzal57; **был :8080** —
переехали 2026-08-14, на хосте его постоянно держит vite соседнего проекта,
и контейнер `web` не поднимался), sales_web :8085
(**API продаж**, `sales-api/`, отдельная БД Postgres `sales`), kkm_web :8087 (**KKM API**,
`kkm-api/`, БД Postgres `kkm`), ais_web :8086 (**AIS API**, `ais-api/`, БД Postgres `ais`;
:8082 на хосте занят посторонним Apache), frontend :3000 (Nuxt + Nuxt UI), ais_spa :3001
(SPA отчётов АИС), db :5432, firebird :3050, legacy АИС :8090 (`ais/`), legacy сайт :8091
(`avtovokzal57/`).
**Сколько запросов приложение тянет одновременно — `docker/php/pool.conf`**
(монтируется как `/usr/local/etc/php-fpm.d/zzz-pool.conf`; имя на `zzz`,
потому что конфиги в образе подключаются по маске `*.conf` в алфавитном
порядке и переопределить `www.conf` может только файл после него).
Потолок у каждого приложения свой — переменная `PHP_FPM_MAX_CHILDREN` в
compose: backend 24, sales-api 24, ais-api 12, kkm-api 8 (дефолт 10 задан
в Dockerfile, чтобы контейнер поднимался и без переменной). **ЛОВУШКА
синтаксиса:** подстановка работает только как `${ПЕРЕМЕННАЯ}` — вариант
`$ПЕРЕМЕННАЯ` php-fpm не разворачивает и падает с «unable to parse value
for entry 'pm.max_children'».
**Зачем это заведено:** в образе `php:8.5-fpm` стоит `pm.max_children = 5`,
а один обработчик backend занимает 50–56 МБ — то есть потолок пула был
280 МБ при 15 ГБ памяти на сервере, зато ПЯТИ одновременных запросов
хватало, чтобы приложение перестало отвечать всем. 16.11.2026 так и
вышло: запросы к недоступным станциям держались по 21–120 с, заняли все
пять обработчиков backend и sales-api, и сайт отдавал «Server Error» даже
там, где станции не нужны, а письма о покупке уходили без PDF (gotenberg
не мог получить печатную форму). Там же `pm.max_requests = 500` —
страховка от утечек в долгоживущем процессе (в образе 0, то есть никогда
не перезапускать).
**Лимиты PHP — один файл `docker/php/php.ini` на все четыре приложения**
(`memory_limit = 512M`, `max_execution_time = 300`, загрузка 64M, opcache
с `validate_timestamps=1`): он называется «для разработки», но едет и на
прод — правки касаются сразу всех.
**Ошибки PHP: в вебе не показываем, в журнал пишем ОБЯЗАТЕЛЬНО.**
`display_errors` выключен для веба через `php_admin_flag` в
`docker/php/pool.conf` (переменная `PHP_DISPLAY_ERRORS`, по умолчанию
`off`, включается в корневом `.env`) — покупателю незачем видеть путь к
файлу, строку и кусок кода. В самом `php.ini` показ оставлен **включённым
ради консоли**: artisan и разовые скрипты читает человек, который их и
запустил, а `php_admin_flag` действует только на php-fpm.
**ЛОВУШКА, из-за которой выключать было нельзя «просто так»:** в образе
`php:8.5-fpm` своего php.ini нет, действуют встроенные умолчания, а там
**`log_errors = 0`** — то есть фатальные ошибки PHP (падение при
компиляции файла, нехватка памяти, сбой расширения) не попадали НИКУДА:
в вебе их видел покупатель, и больше никто. Выключение показа просто
потеряло бы их. Поэтому в php.ini добавлен `log_errors = On`, а
`error_log` оставлен ПУСТЫМ сознательно: тогда PHP отдаёт ошибку журналу
SAPI, то есть php-fpm, а тот пишет её в stderr контейнера
(`docker compose logs app`) — отдельный файл пришлось бы ещё и
ротировать. Проверка: фатальная ошибка в `public/*.php` не должна
появиться в ответе и ДОЛЖНА появиться в `docker compose logs`.
**Журналы контейнеров ротируются** (`x-logging` в compose, 20 МБ × 5):
драйвер json-file по умолчанию не ограничен ничем, и на проде эти файлы
набрали 295 МБ (крупнейший — 176 МБ у frontend). Задано у сервисов, а не
в `/etc/docker/daemon.json`, чтобы не перезапускать демон docker со всеми
чужими контейнерами; применяется при пересоздании контейнеров, то есть
обычным деплоем.
**ЛОВУШКА: у nginx свой таймаут, и он короче.** `fastcgi_read_timeout` по
умолчанию 60 с, то есть при `max_execution_time = 300` сотрудник получал
**504 от nginx** раньше, чем PHP успевал ответить. У `ais.conf` он поднят
до 300 с (отчёты идут по базам всех станций хозяйства); у сайта, API
продаж и KKM оставлено умолчание — там все запросы короткие, и 60 с
означает «что-то не так», а не «долгий отчёт». За сутки 16.11.2026
backend отдал **157 ответов 504 и 201 раз 499** (клиент не дождался), из
них 190 — в один час, когда пропала связь со станциями: запросы стояли в
очереди к пяти обработчикам дольше минуты. Среди оборванных было 8
`POST orders/confirm` — то самое дооформление, после которого покупатель
видит «не удалось подтвердить покупку» при списанных деньгах.
**KkmServer** установлен на хост-машине (НЕ docker): systemd `kkmserver.service`,
http://127.0.0.1:5893, виртуальная ККТ NumDevice=1 (эмулятор); из контейнеров доступен
как `host.docker.internal:5893` (extra_hosts host-gateway у kkm_app).
Таблица сервисов — в README.

### Новые сервисы (этап переноса, август 2026)
- **`sales-api/`** — API продаж (Laravel 13): рейсы/места/резерв/продажа/возврат через
  процедуры KS_* Firebird. Работает автономно, без оплат. Журнал всех запросов/ответов —
  Postgres `sales.api_requests`; резервы/продажи/возвраты — свои таблицы. Агенты — Bearer-токен
  (`config/agents.php`) + IP whitelist. Ловушка ID_TIME_PLACES (доли секунды) решена инлайном
  литерала (`BusterConnection::quoteTimestamp`). `GET /trips` без `date` — режим
  «ближайшие» legacy (`blij=1`): рейсы всех дат от сегодняшней, `first 200`;
  `for_sale=0` отдаёт и рейсы, недоступные к интернет-продаже. Ограничения
  продажи по дальности (`min_kilom`/`max_kilom`) считаются после выборки по
  TRACES — как в legacy; ручное перекрытие SALE_BOUND_AFTER (legacy-файл
  `vidjets/ogranichenie.txt`) переехало в `config/sale_bounds.php`.
  **Список пунктов назначения (`GET /stations/{awtcod}/destinations`) сортируется
  в PHP** (`App\Support\StationNameSorter`), а НЕ в запросе: KS_STATIONS отдаёт
  порядок базы — с учётом регистра и знаков, поэтому «АЗС», «СХТ», «ДРСУ-3»
  вставали в начало группы, а «пов.Вепринец», «м-н Москва», «ул. Заводская» —
  в самый конец. Ключ сортировки: нижний регистр, ё→е, всё кроме букв и цифр —
  разделитель, лишние пробелы убраны; сравнение Collator `ru_RU` (без ext-intl
  фолбэк на побайтовое — после нормализации порядок тот же). Та же логика
  добавлена в legacy (`ais/api/sort_help.php` + `api2.php`, выложено на бой
  2026-08-14 с бэкапами `*.bak_20260814`), порядок сверен построчно на боевых
  списках. Селекты сайта менять не пришлось: Nuxt UI при вводе поднимает
  совпадения с начала названия и сохраняет порядок сервера внутри групп; в
  legacy для этого понадобилась своя `score` у selectize (`js/main.js`), иначе
  найденное сортировалось по релевантности — короткие названия вперёд.
- **`backend/`** — высокоуровневое API: заказы (`orders`), оплата Сбербанк через SDK
  `voronkovich/sberbank-acquiring-client` (локально тестовый контур 3dsec/metagraphica),
  подтверждение оплаты + оформление, возврат по коду (`refunds/preview|confirm`, таблица
  `refunds`, подписанный Crypt-токен подтверждения), данные печати (`orders/{id}/print`,
  обезличивание 30 дней), билеты одним PDF (`orders/{id}/pdf`).
  **Незавершённые покупки** (`POST orders/pending`): покупатель ушёл на шлюз и не
  вернулся — заказ есть, билетов нет. Заказ ищется по идентификаторам из
  `localStorage` браузера И по `user_id` (у кабинета — с любого устройства);
  состояние считается по статусу заказа и `getOrderStatusExtended` шлюза:
  `awaiting_confirmation` (деньги у нас, билетов нет) или `awaiting_payment`
  (ещё можно оплатить, пока жива бронь). Срок оплаты — минимум из
  «создан + 24 мин» (столько держит `KS_BRONTIME_PLACE`) и «отправление −
  32 мин». В legacy это жило в PHP-сессии и умирало вместе с ней.
  **Правило детского тарифа** (`config/sale_rules.php`, `CHILD_TARIFF_REQUIRES_ADULT`
  и `MAX_CHILDREN_PER_ADULT`): детский билет только вместе с полным, не более N
  на взрослого — перенос legacy (`js/passengers.js` + `url/passengers.php`),
  но выключаемый. Форма покупки читает те же значения через
  `GET /api/v1/sale-rules`. Пункт «Детский» из списка НЕ убираем — исчезнувший
  пункт покупатель не заметит и не поймёт, почему детского билета нет; вместо
  этого выбор не применяется и показывается уведомление с текстом legacy.
  **Брошенные покупки** — команда `orders:cancel-abandoned` (ofelia, каждые
  15 минут; перенос legacy `avtovokzal57/refund.php`): деньги списаны, билетов
  нет, покупатель не вернулся. Билеты за него **не оформляем** — он мог об
  этой покупке и не знать; просто возвращаем деньги. **ЛОВУШКА:** отмена
  (`reverse`) работает только внутри операционного дня шлюза — оплата в 23:50
  и отмена в 00:50 уже не пройдёт, поэтому при отказе отмены делается полный
  возврат (`refund`); он идёт дольше и виден покупателю отдельной операцией,
  поэтому именно аварийный. Не вышло ни то, ни другое — заказ НЕ трогаем
  (деньги остаются у нас, решать человеку) и пишем на support, как делала
  `failnotify` в legacy. Сроки — `config/orders.php`
  (`ORDER_ABANDON_AFTER_MINUTES`, по умолчанию час; legacy ждал 40 минут).
  **Отказ от заказа** (`POST orders/{id}/cancel`): снимает бронь мест и
  отменяет регистрацию платежа. Бронь снимает sales-api
  (`DELETE reservations/{id}` → `KS_ABO_BRONTIME_PLACES`) — процедура убирает
  TimeMark и работает только для того агента, кто бронь ставил. Оплаченный
  заказ так отменить нельзя: деньги уже у нас, его либо дооформляют, либо
  возвращают. Статус шлюза при отмене важнее нашего — деньги могли списаться
  минуту назад, а возврата со шлюза мы ещё не видели.
  **Дооформление идёт под блокировкой на заказ** (`Cache::lock('order-confirm:…')`
  в `OrderService::confirm`, рядом — `Cache::lock('sale:<reservation_id>')` в
  sales-api `SaleController`). Страница результата способна прислать два
  `orders/confirm` в одну секунду: оба проходили проверку статуса и оба шли в
  `KS_SALE_PLACES` по одному резерву (`sold` у резерва ставится ПОСЛЕ продажи,
  то есть окно ~1 с), Firebird отвечал дедлоком `-913`, а `catch` писал заказу
  `failed` ПОВЕРХ уже оформленного `completed`. Снаружи это выглядело так:
  деньги списаны, билет на станции продан, чек пробит, код возврата выдан — а
  покупатель видит «Не удалось подтвердить покупку», печать и возврат по коду
  не работают (ловилось на проде 15.11.2026, заказ
  `01a1e0d8-e905-7003-a8a9-3f6387807ee1`). Поэтому: второй запрос ЖДЁТ
  (`block(30)`) и получает готовый заказ; дедлок Firebird распознаётся как
  `concurrent_sale` (`BusterGateway::translateConflict`), и на конфликтные
  коды (`already_sold`/`concurrent_sale`/`sale_in_progress`) статус заказа
  **не портится вовсе**; сам `catch` пишет `failed` условным UPDATE'ом
  `where status != 'completed'`.
  **Страница `/print/{id}` при отсутствии данных отвечает 404**, а не 200: по
  этому же адресу gotenberg рендерит PDF для письма и считал страницу
  «Информация по заказу не найдена» нормальным билетом (в логе оставалось
  `"pdf":true`). Плюс `SendPurchaseEmail` вообще не рендерит PDF, если заказ
  не `completed` или билетов нет.
  **ЛОВУШКА `SBERBANK_API_URI`: только схема и хост, без пути.** SDK сам
  приклеивает префикс (`Client::API_PREFIX_DEFAULT = '/payment/rest/'`,
  `Client::execute()`: `$uri = $apiUri . $action`), поэтому адрес с
  `/payment/rest/` на конце даёт `…/payment/rest//payment/rest/register.do`
  и шлюз отвечает **404** — заказ не создаётся, в логе `Bad HTTP code: 404`
  из `PaymentGateway->register`. Ловилось на проде 2026-11-14.
  **ЛОВУШКА: у вызовов шлюза ОБЯЗАТЕЛЬНЫ свои таймауты** (задано
  17.11.2026, `services.sberbank.connect_timeout` = 10 с и
  `timeout` = 30 с, переменные `SBERBANK_CONNECT_TIMEOUT` /
  `SBERBANK_TIMEOUT`). Своих таймаутов SDK не ставит —
  `HttpClient\CurlClient` прокидывает ровно те опции, что ему дали, а у
  libcurl умолчание `CURLOPT_CONNECTTIMEOUT` — **300 секунд**. У боевого
  хоста ДВА адреса (`3dsec-payments.yookassa.ru` → 109.235.165.36 и
  185.71.78.36), и когда один залипает (пакеты уходят в пустоту, а не
  отказом), libcurl делит предел между адресами и ждёт все пять минут.

  перехода на альтернативную версию с любой страницы.
  **Название «АО «Орелавтотранс» не обрезается** многоточием: на телефоне
  оно переносится на вторую строку (по пробелу после «АО») и набрано
  мельче, от `sm` — одна строка (`sm:whitespace-nowrap`), иначе на
  десктопе меню наезжало на вторую строку названия.
  **Многоточий на сайте нет вообще:** утилита `truncate` отменена
  глобально в `main.css` — её ставит и тема Nuxt UI (подписи кнопок,
  выбранное значение селекта, пункты списков), а за многоточием исчезало
  именно то, по чему различают станции и рейсы.
  **Кнопка «Назад» — компонент `BackButton.vue`** (рейсы, расписание, тариф):
  настоящий `router.back()`, а не ссылка на главную, иначе терялись маршрут
  и дата поиска. Истории может не быть (заход по прямой ссылке) — это видно
  по `window.history.state.back`, тогда уходим на `fallback`. Полоса
  `sticky top-16` — ровно под шапкой сайта (она `sticky top-0`, 64px).
  Форма поиска на главной переживает возврат: её состояние лежит в
  `sessionStorage` (`home-search`), в адресе главной его нет. Остановку
  подставляем только после загрузки списка станции и только если она в нём
  ещё есть.
  **Поля ввода с маской** — `MaskedInput.vue` (библиотека `maska`), поверх него
  `DateInput.vue` (дата рождения `дд.мм.гггг` вместо `type=date`: нативный
  календарь на телефоне неудобен; наружу отдаёт ISO, `v-model:invalid`
  сигналит о несуществующей дате) и `PhoneInput.vue` (`+7 (###) ###-##-##`,
  галочка «Городской / зарубежный номер» маску снимает целиком). Маска серии
  и номера документа — только для паспорта РФ (`#### ######`), у остальных
  документов формат разный. **ЛОВУШКА:** директиву `v-maska` на `UInput`
  вешать нельзя — директива на компоненте применяется к его КОРНЕВОМУ
  элементу, а у UInput это обёртка `<div>`; маска навешивается на нативный
  input из `defineExpose({ inputRef })`, и у таких обёрток обязателен
  `inheritAttrs: false`, иначе обработчики срабатывают дважды.
  **`ResponsiveSelect.vue`** — выпадающий список: на десктопе обычный
  USelectMenu, на узком экране раскрывается на ВЕСЬ экран (закреплены стрелка
  «назад» и поиск, прокручивается только список) — пунктов назначения бывает
  больше двух сотен, и в маленьком окошке их приходилось листать целиком.
  Используется для «Откуда»/«Куда», места, гражданства, документа и выбора
  пассажира из профиля; у места поиск выключен (`:searchable="false"` — это
  номера). **ЛОВУШКА при открытии ИЗ модального окна** (форма пассажира в
  кабинете): панель телепортируется в `body`, то есть ВНЕ диалога, а Reka на
  время окна гасит указатель всему снаружи (`body { pointer-events: none }`)
  и закрывает диалог по нажатию «снаружи». Поэтому у панели явный
  `pointer-events: auto` и `@pointerdown.stop` — без первого по пунктам не
  попасть, без второго выбор документа закрывал форму пассажира.
  **Модальные окна на телефоне разворачиваются во весь экран** —
  `MOBILE_FULLSCREEN_MODAL` из `useModalUi`: в карточке по центру длинный
  текст превращается в колодец, а ряд из трёх кнопок ломается на две строки. Названия нигде не
  обрезаются многоточием — ни в поле, ни в списке. Обе версии рендерятся
  всегда и переключаются классами (`md:hidden`), а не проверкой ширины в JS:
  при SSR ширина неизвестна и разметка разошлась бы.
  **Дата «сегодня» — только через `useSiteDate`** (`siteDate`,
  `siteDateShifted`). `new Date().toISOString()` даёт UTC, и с полуночи до
  трёх ночи по Москве «сегодня» оказывалось ВЧЕРАШНИМ числом — форма поиска
  и ссылки «Сегодня/Завтра/Послезавтра» уводили на прошедший день
  (ловилось на проде 2026-11-14). Считаем в поясе автовокзала
  (`Europe/Moscow`), а не устройства: времена рейсов BUSTER — московские
  wall-clock, и SSR с клиентом так дают одну и ту же дату.
- **Версия сайта для людей с нарушениями зрения** (ГОСТ Р 52872-2019, WCAG 2.1 AA;
  в legacy её не было — переносить было нечего): кнопка «Для слабовидящих» в
  шапке (`AccessibilityToggle.vue`) включает режим, настройки — в полосе над
  шапкой (`AccessibilityPanel.vue`), по умолчанию **свёрнутой**: включение
  режима не должно отодвигать страницу вниз экраном настроек. Состав —
  размер шрифта (3 шага), цветовая схема (три обязательные по ГОСТ: чёрным на
  белом, белым на чёрном, тёмно-синим на голубом, плюс коричневым на бежевом),
  изображения вкл/выкл, кернинг, межстрочный интервал, шрифт с засечками,
  «Обычная версия сайта» и сброс. Выключается целиком одной переменной:
  **`ACCESSIBILITY_VERSION=0`** в корневом `.env` (compose →
  `NUXT_PUBLIC_ACCESSIBILITY`), тогда нет ни кнопки, ни панели, ни класса на
  `<html>`.
  **Устройство — одно и главное: обычный режим не затрагивается.** Настройки
  (`useAccessibility.ts`) превращаются в классы на `<html>` (`a11y`,
  `a11y-scheme-*`, `a11y-font-*`…), и ВСЕ правила режима лежат в отдельном
  `app/assets/css/accessibility.css`, где каждый селектор начинается с
  `html.a11y`. Пока режим выключен, класса нет — ни одно правило не применяется.
  Состояние — в **cookie** `a11y`, а не в localStorage: класс нужен уже в
  SSR-разметке, иначе страница сначала показалась бы обычной и только потом
  перекрасилась. Cookie читается как чужие данные (`sanitize`).
  **Перекраска — двумя цветами схемы.** Обычная поверхность (страница,
  карточки, поля, выпадающие списки) — фон схемы и рамка цветом текста;
  акцентная (шапка, подвал, сплошные кнопки, выбранные пункты) — **инверсия**.
  Фон у блоков именно МЕНЯЕТСЯ: первая версия снимала его в прозрачный, и
  шапка с кнопками сливались со страницей — выглядело как сломанная вёрстка.
  **Ловушки, уже учтённые (не сломать при правках):**
  - `transform` НЕ сбрасываем — на нём держится позиционирование выпадающих
    списков и центрирование модалок (иначе все всплывающие слои собираются в
    левом верхнем углу).
  - `box-shadow` НЕ сбрасываем — на нём в теме Nuxt UI держатся рамки `ring-*`,
    то есть границы карточек, полей и панелей; снятие теней убирало границы
    блоков вместе с ними. Цвет им задают переопределённые `--ui-border` и др.
  - Иконки — это `<span class="iconify">` с `mask-image` и заливкой
    `currentColor`: фон схемы делает их невидимыми, заливку возвращаем отдельным
    правилом.
  - Правило по образцу `[class*="bg-error/"]` ловит `hover:bg-error/75` у
    СПЛОШНОЙ кнопки и ломает её инверсию — подпись пропадает (кнопка «Найти
    билеты» выходила чёрной на чёрном). Для полупрозрачных подложек отдельное
    правило не нужно: общий сброс и так красит их фоном страницы.
  - Декоративные накладки `absolute inset-0` (затемнение под заголовком
    главной, градиент под подписями плиток) остаются прозрачными — иначе
    закрыли бы и картинку, и текст.
  - Всплывающим слоям (`[role=dialog|menu|listbox]`,
    `[data-reka-popper-content-wrapper] > *`) фон ОБЯЗАТЕЛЕН.
  - Логотип `public/img/logo.png` — силуэт ЧИСТО БЕЛЫМ по прозрачному фону,
    поэтому на схеме «белым на чёрном» (полоса шапки становится белой) он
    инвертируется (`html.a11y-scheme-black header img`).
  - `<iframe>`/`<svg>` при выключенных картинках не прячем — в кадре капча
    формы обратной связи.
  - В самой панели свои интервалы (`letter-spacing: normal`,
    `line-height: 1.3`), кнопки панели не сжимаются (`flex: none`): с общими
    интервалами кружок-образец цвета вылезал за край своей кнопки, а общее
    `min-width: 0` позволяло флексу ужать кнопку уже её собственной подписи.
  - **`height: auto` у кнопок ломает КВАДРАТНЫЕ контролы.** Чекбокс, радио и
    переключатель в теме — это `<button role="checkbox">` с фиксированным
    `size-*`; «высота по содержимому» схлопывала их в полоску 21×4px (галочку
    «Я даю согласие…» было не видно и не во что нажать). Они исключены из
    правила через `:not([role=...])`, их размеры в `rem` и так растут с кеглем.
  - **`height: auto` у картинок ломает `object-cover`.** Снимок плитки
    «Популярные направления» (`absolute inset-0 w-full h-full object-cover`)
    получал натуральную высоту, не влезал в плитку и обрезался произвольным
    куском. У картинок задаём только `max-width`. Сама плитка перевёрстана:
    снимок **не увеличивается** (`width: auto`, потолок 400px у плитки и
    260px по высоте снимка — в пикселях, по размеру самих файлов 277–673px,
    а не в `rem`), подпись под ним. Растянутый на весь экран снимок 347px —
    мутное пятно, в котором слабовидящему всё равно нечего разобрать.
  - **Одной колонки мало, пока жив `col-span-*`.** Элемент на две колонки при
    единственной явной заставляет сетку создать НЕЯВНУЮ вторую размером
    `auto`: колонка настроек схлопывалась до 6px, и образец размера шрифта не
    помещался в кнопку. Поэтому рядом с `grid-template-columns: 1fr` стоит
    `grid-column: auto`. Исключений из «одной колонки» два, обоим колонки
    возвращены медиазапросами: панель настроек (в один столбец семь групп
    занимают пол-экрана) и плитки направлений (каждая не шире 400px, и в
    одну колонку они дали бы длинный столбец с пустым полем справа).
  - **Шапка не переносится — но только до `xl`.** Общий `flex-wrap` уносил
    кнопку меню на вторую строку, и шапка съедала треть экрана телефона. Ряд
    шапки — `nowrap`, кнопка меню всегда в правом углу, переносится НАЗВАНИЕ,
    логотип ниже 640px скрыт. Выше `xl` запрет снят: там не «бургер», а меню
    из пяти пунктов, и `nowrap` сжимал название до ширины колонки —
    «Орелавтотранс» разрывалось посреди слова. Граница та же, что у обычной
    шапки (меню из пунктов появляется с 1280px). Строка с галочкой тоже `nowrap`: иначе квадратик оставался
    один на строке, а подпись уезжала под него.
  - Тонкие разделители (`h-px bg-default` вокруг «или») общий сброс красил
    фоном страницы, и они пропадали — им отдельно возвращается цвет текста.
  **Вёрстка в режиме перестраивается, горизонтальной прокрутки быть не должно**
  (WCAG 1.4.10): ряды переносятся (`flex-wrap`, кроме `flex-col` и кроме рядов
  ВНУТРИ кнопок — там перенос означал бы «стрелка списка уехала под текст»),
  многоколоночные сетки становятся одной колонкой, `truncate`/`whitespace-nowrap`
  отменяются (не влезло — переносим, а не прячем за многоточием), фиксированные
  `min-w-*` обнуляются, у кнопок высота по содержимому. Размер шрифта задаётся
  КОРНЮ (вместе с текстом пропорционально растут rem-отступы), а **на экранах
  уже 480px шаги мельче** (17/20/22 вместо 18/22/26): на 320px при 26px от
  ширины экрана на текст не остаётся ничего.
  Проверка — прогон вёрстки по всем публичным страницам в iframe заданной
  ширины: ищется переполнение страницы, элементы за краем экрана, обрезанный
  многоточием текст и кнопки, у которых содержимое больше их самих. Прогнано на
  320/360/390/414/768/1024/1280/1440 во всех схемах и шагах шрифта, и в обычном
  режиме для сравнения. Тем же прогоном найдены и исправлены два дефекта
  ОБЫЧНОГО режима на 320px: кнопка «Перейти к оплате» уезжала за край экрана
  (`buy.vue`, не хватало `flex-wrap`) и таблица реквизитов растягивала страницу
  до 372px (`contacts.vue`, не было обёртки с прокруткой).
  Печатные формы (`/print/{id}`, `layout: false`) режима не знают, и в
  `@media print` он отключается принудительно: лист всегда чёрным по белому.
- **PWA: приложение на телефоне и купленные билеты без интернета**
  (в legacy ничего подобного не было — переносить было нечего). Сайт
  ставится на домашний экран (`public/manifest.webmanifest`, иконки
  `public/icons/`), а **купленные билеты открываются без сети** — ради
  этого всё и сделано: в автобусе связи может не быть, а билет показать
  надо.
  **Стартовый экран приложения — `/app`** (`start_url` манифеста), а НЕ
  главная: главная про одно действие (поиск рейса) и наполовину занята
  картинкой с формой, тогда как приложение открывают и ради билета в
  дороге, и ради телефона автовокзала. На экране четыре плитки —
  «Новости» (`/news`), «Покупка билета» (`/`), «Мои билеты»
  (`/tickets`), «Контакты» (`/contacts`) — плюс расписание и возврат
  билета. Разделы, которым нужна сеть, **без неё помечены «Нужен
  интернет»** и не кликаются: иначе покупатель тыкал бы в плитку и
  получал страницу «нет подключения». В приложении (`display-mode:
  standalone`) логотип в шапке ведёт на `/app`, а не на главную, и в
  мобильном меню появляется пункт «Главный экран» — иначе со стартового
  экрана не было бы дороги обратно.
  Плитка «Новости» ведёт в настоящий раздел — см. «Новости и объявления».
  **Предложение войти в кабинет** (`AppLoginPrompt` на `/app`): карточка
  на экране висит постоянно, окно показывается **не чаще раза в неделю**
  (отметка в `localStorage`) и только при сети — без неё войти всё равно
  нельзя, а место на экране оно займёт. Срок жизни самой авторизации не
  трогали: полгода бездействия, продлеваемые при каждом заходе (и
  cookie, и `last_used_at` токена) — тот, кто открывает приложение хотя
  бы раз в полгода, не разлогинится никогда.
  **Данные билетов — IndexedDB, а не кэш service worker**
  (`app/composables/useOfflineTickets.ts`, база `avtovokzal-offline`):
  кладётся ответ `GET /orders/{id}/print` — тот же, из которого рисуется
  печатная форма и PDF. Ответы API в Cache Storage не попадают вовсе: они
  ходят с Bearer-токеном кабинета, а в билете лежат ФИО и номер
  документа. Сохраняется билет **сразу после оформления** (страница
  `/payment/result`, в том числе гостю — кабинета у него нет) и при
  заходе в кабинет (`/lk` подтягивает предстоящие поездки, они же
  обновляются при открытии `/tickets`). Чистится само: через сутки после
  отправления рейса, через 30 дней от сохранения (дальше backend всё
  равно обезличивает), **и целиком при выходе из кабинета** —
  но именно в `logout()`, а НЕ в `forgetSession()`: вторая срабатывает и
  когда `/auth/me` не ответил из-за сети, то есть билеты стирались бы
  ровно тогда, когда нужны.
  **Service worker (`public/sw.js`) написан руками**, без workbox и
  `@vite-pwa/nuxt`: нужны три стратегии, а сборочный precache-манифест
  плохо ложится на SSR (оболочку отдаёт Nitro, а не статический
  index.html). Он кэширует оболочки `/app`, `/tickets` и `/offline` (все
  `ssr: false` в `nuxt.config.ts` — иначе в кэш попала бы SSR-разметка с
  чужими персональными данными), статику `_nuxt/*` и картинки
  (cache-first, имена с хэшем), а навигации ведёт network-first с
  откатом на `/offline`. **VERSION в файле поднимается руками** — по ней
  чистятся старые кэши.
  **`/contacts` — единственная СЕРВЕРНАЯ страница в кэше** (её читают
  поисковики, `ssr: false` ей нельзя): в кэш ложится готовая разметка с
  адресами и телефонами, поэтому без сети она открывается вообще без
  запросов — данные уже внутри HTML. Из личного там только e-mail в
  шапке, и при выходе из кабинета кэш оболочек стирается целиком
  (сообщение `CLEAR_SHELL`, `clearOfflineShell()`).
  **Ловушки, уже учтённые (не сломать при правках):**
  - **Регистрацию нельзя вешать только на `window.onload`.** Страницы
    `/tickets` и `/offline` рендерятся в браузере, их гидрация идёт ПОСЛЕ
    загрузки документа — событие уже прошло, и service worker не
    регистрировался ровно там, где он нужен. В плагине
    (`plugins/pwa.client.ts`) проверяется `document.readyState`.
  - **Манифест отдаётся network-first, а не как остальная статика.**
    Лежал среди `_nuxt/*` и картинок (cache-first) — и браузер при
    установке читал СТАРУЮ копию: с прежним `start_url` и прежними
    настройками. Снаружи это выглядит как «приложение ставится не тем,
    чем должно». Ловилось 15.11.2026 при переезде `start_url` на `/app`.
  - **«Ставится ярлык, а не приложение» — обычно НЕ поломка сайта.** На
    Android удаление иконки с домашнего экрана не удаляет само
    приложение (WebAPK): оно остаётся в системе, Chrome считает его

- **Подтверждение e-mail кодом из письма (6 цифр)** — таблица **`auth_codes`**,
  сервис `AuthCodeService`, лимиты в `config/site.php` → `auth_code`
  (сделано 15.11.2026). До этого регистрация **вообще не подтверждала
  адрес**: кабинет открывался сразу, а по `orders.email` ему видны покупки,
  сделанные на этот адрес до регистрации — то есть на чужой адрес можно
  было завести кабинет и увидеть чужие билеты с ФИО и документами. В legacy
  такой дыры не было: там пароль не задавался, а **генерировался и уходил
  письмом** (`url/register.php`, ветка при `$CONFIG['reg_mode'] != 'code'`).
  Правила кода: живёт **30 минут**, **5 попыток** ввода на пару «адрес +
  код» (счётчик в БД — требование «неважно с какого браузера»), повторная
  отправка **не чаще 3 минут**, **не более 5 кодов на адрес в сутки**
  (отдельно по каждому процессу: общий потолок закрыл бы восстановление
  пароля тому, кто перед этим не смог зарегистрироваться). Исчерпали
  попытки — код гасится (`blocked_at`), нужен новый. В базе **bcrypt**
  кода, а не sha256: у шестизначного кода всего миллион значений.
  **Пользователь при регистрации создаётся ТОЛЬКО после кода** — данные
  (хэш пароля и телефон) ждут в `auth_codes.payload`, иначе неподтверждённый
  кабинет занимал бы чужой адрес. Три процесса на кодах: регистрация
  (`POST auth/register` → `auth/register/confirm`), восстановление пароля
  (`auth/password/forgot` → `auth/password/reset` с `email`+`code`), добавление
  e-mail кабинету из VK (`auth/email` → `auth/email/confirm`, уже под
  `auth:sanctum` — привязать адрес можно только своему кабинету).
  Повторная отправка — `auth/code/resend`. **ЛОВУШКА лимита запросов:**
  маршруты ввода кода вынесены в `throttle:30,1` — на общих `throttle:10,1`
  человек, пару раз ошибившийся цифрой, получал «Too Many Attempts» вместо
  подсказки; само по себе это не ослабление, перебор закрывают 5 попыток в
  БД. Английский текст 429 тоже убран — `ThrottleRequestsException`
  рендерится по-русски в `bootstrap/app.php`.
  Фронт: `AuthCodeForm.vue` (UPinInput на 6 цифр, автоотправка по последней
  цифре, отсчёты **из ответа сервера** — своих констант фронт не держит,
  иначе «отправить снова» включалось бы раньше, чем сервер готов).
  Страницы `/reset` и `/confirm-email` остались **редиректами** на `/forgot`
  и `/lk/profile` — ради писем, отправленных до перехода.

- **Вход через VK ID** (в legacy входа через соцсети не было — новая
  возможность): OAuth 2.1 + PKCE **без JS-SDK**. Кнопка — обычная ссылка на
  серверный маршрут Nuxt `/auth/vk`, тот спрашивает у backend адрес
  авторизации (`auth/vk/start`, там же генерируются code_verifier и state) и
  уводит на `id.vk.ru/authorize`; возврат ловит `/auth/vk/callback`, код на
  токен меняет backend (`auth/vk/callback` → `VkIdClient`), а Nuxt кладёт
  выданный Sanctum-токен в ту же httpOnly cookie `av_session`. client_id и
  обмен кода фронту не видны. **state одноразовый**: verifier лежит в кэше
  backend (сессии у API нет) и вынимается через `Cache::pull`, плюс дубль
  в httpOnly cookie `vk_state` — сверка защищает от подсунутого чужого кода.
  Токен VK после получения профиля гасим (`/oauth2/logout`) — ходить в VK
  от имени покупателя мы не собираемся. Ключи — `VK_CLIENT_ID` /
  `VK_CLIENT_SECRET` (`config/vk.php`); **пустой client_id = вход выключен**,
  кнопки нет (тестовых приложений VK не выдаёт, как и у SmartCaptcha).
  Адрес возврата собирается ТОЛЬКО из конфига (`VK_REDIRECT_URI`, иначе
  `FRONTEND_URL`), а не из запроса: он обязан совпадать байт в байт в
  настройках приложения VK, в `/authorize` и в `/oauth2/auth`.
  **VK принимает только https и только стандартный порт**, поэтому на
  локальном контуре поднят https-вход: сервис `proxy` (Caddy,
  `docker/caddy/Caddyfile`, порт **443**, самоподписанный `tls internal`),
  сайт открывается как **https://avtovokzal57.local** — имя прописано в
  `/etc/hosts` (127.0.0.1). Он отдаёт под
  ОДНИМ origin и сайт, и `/api/v1/*` — со страницы по https браузер не даст
  обратиться к http-API (mixed content); `useApi` это учитывает
  (`browserApiBase`: при https-странице базой становится origin). Только
  `/api/v1/*`, потому что `/api/auth/session` — собственный маршрут Nuxt.
  В Caddyfile имена сайта заданы явно (`avtovokzal57.local`, `localhost`,
  `127.0.0.1`): для безымянного блока `tls internal` не может выпустить
  сертификат и рвёт рукопожатие. `VK_REDIRECT_URI` на локальном контуре
  указывает на это имя, http://127.0.0.1:3000 продолжает работать как раньше.
  **Кнопка ведёт ПРЯМО на `id.vk.ru`**, а не на наш `/auth/vk`: такую ссылку
  телефон отдаёт приложению VK (Android App Links / iOS Universal Links), и
  вход происходит в один тап. Через `/auth/vk` этого не было — там
  302-редирект, а на редиректах система ссылку приложению не передаёт и
  открывает веб-форму. Адрес кнопка получает заранее у серверного маршрута
  `/api/auth/vk/start` (он же кладёт `vk_state` в cookie); пока ответа нет
  и при выключенном JS в `href` остаётся прежний `/auth/vk`.
  **E-mail от VK может не прийти** (нет у аккаунта или не дали доступ) —
  по решению заказчика такой кабинет заводится всё равно: `users.email`
  **nullable**, почту потом *предлагаем* (страница профиля, редирект
  `/lk/profile?add-email=1` сразу после первого входа), но не требуем.
  **Покупать без почты тоже можно:** на форме покупки поле необязательно для
  авторизованного (гостю по-прежнему обязательно), а в заказ уходит
  служебный адрес `site.fiscal_fallback_email` (`FISCAL_FALLBACK_EMAIL`).
  Он нужен фискальному чеку — по 54-ФЗ электронный чек надо куда-то
  отправить, и пустой адрес ККТ не примет. **НАШИ письма на этот адрес не
  идут** (билеты, приглашение в кабинет, уведомление о возврате — проверка
  `OrderService::isFiscalFallbackEmail`), и по нему же не ищутся заказы
  кабинета: ящик общий, иначе по нему сошлись бы покупки разных людей.
  Записать введённый адрес сразу нельзя — кабинет показывает покупки по
  `orders.email`, поэтому владение подтверждается **кодом из письма**
  (`auth_codes` type=`email_confirm`, ввод прямо в профиле); адрес,
  пришедший от VK, считается подтверждённым сразу. Если e-mail от VK совпал

  с теми же покупками не заводим). У кабинета без пароля профиль показывает

  нельзя), а форма покупки не блокирует поле e-mail — брать его неоткуда.

  стирает номер): кабинет из VK может остаться вообще без контактов. При
  регистрации по e-mail и в форме покупки номер по-прежнему обязателен.

  регистрации, модалка на `/buy`, предложение в приложении): это вход в

- **ВРЕМЯ ПРИБЫТИЯ СЧИТАЕТСЯ ТОЛЬКО ПО «ВРЕМЕНИ В ПУТИ»** (исправлено
  17.11.2026). `TIME_TO_END` у рейса — это **TIME, то есть время суток**:
  в базе станции оно получается как `evryraice.timestart +
  tracetime.time_to_stat*60`, и Firebird при сложении **оборачивает его
  через 24 часа**. У рейса Орёл–Симферополь в пути 1535 минут (25 ч 35
  мин), отправление 11:15 — и `TIME_TO_END` равен **12:50**, ровно как у
  рейса, приезжающего в день отправления. Поэтому:
  - sales-api отдаёт у рейса **`time_way_minutes`** (`tracetime.time_to_stat`),
    и прибытие считается как «отправление + минуты» — общий
    `frontend/app/composables/useTripArrival.ts` (`tripArrival`,
    `tripArrivalDayOffset`), им пользуются и `/trips`, и `/buy`;
  - **прежняя догадка «прибытие раньше отправления? значит плюс сутки»
    негодна в принципе**: она добавляет максимум одни сутки, а на этом
    рейсе не добавляла вовсе (12:50 > 11:15) — пассажиру показывалось
    18 ноября вместо 19-го. На `/buy` было грубее: под временем прибытия
    стояла дата ОТПРАВЛЕНИЯ, всегда;
  - legacy в списке рейсов печатал ОДНО ВРЕМЯ без даты
    (`index2.php`: `MB_SUBSTR($value['TIME_TO_END'],0,5)`), то есть
    неверной даты не обещал — её добавил новый сайт. Это наша регрессия,
    а не перенос;
  - на `/tarif` у остановок дальше суток пути теперь стоит пометка
    **«(+N сут.)»** (`arrival_day_offset` у остановки). Legacy печатал
    только `H:i` (`tarif.php`: `date('H:i', strtotime(TIMESTART) +
    TIME_TO_STAT*60)`) — время верное, но по таблице рейса Орёл–Ялта было
    не понять, что все четыре остановки на следующих сутках;
  - **прибытие может быть НЕИЗВЕСТНО** (`time_way_minutes = null`,
    `arrival = null`): у рейса нет строки `tracetime` для этой остановки.
    Тогда `TIME_TO_END` равен времени ОТПРАВЛЕНИЯ, и показывать его
    нельзя — ставим прочерк и «время прибытия уточняйте на станции».
    Legacy приводил NULL к нулю и писал «прибытие = время отправления,
    время в пути 0 ч. 0 мин.».
- **ДЕФЕКТ LEGACY, ИСПРАВЛЕННЫЙ ЗДЕСЬ: рейс без времени в пути до
  остановки выпадал из списка целиком** (`BusterGateway::routes`,
  17.11.2026). Запрос рейсов — это UNION двух ветвей: первая требует
  строку `tracetime` ИМЕННО для запрошенной остановки (`left outer join`
  плюс условие в `where` работает как inner), вторая в legacy
  (`ais/api/api2.php`) ловила только `evryraice.tracetimecod is null` —
  рейсы вообще без расписания остановок. Между ними оставалась **мёртвая
  зона**: расписание у рейса есть, а строки для этой остановки в нём нет —
  и по запросу «от станции до остановки» рейс не показывался ВООБЩЕ, хотя
  билет до неё продаётся (`TARIFS2D.paysoftall > 0`, `prim = 1`).

  «рейс × остановка» из 6506**: «Орел → Дв.спорта» не показывал ни одного
  рейса до Моховицы, «Орел → Госуниверситет-УНПК» — до Маслово, то же у
  Ветлечебницы, Карачевского шоссе и Маслово пов.

  рейсов неизвестно, см. выше.

  «не оплатил» был `silver`, а `red` — только «оплата не отменена». Поэтому
  `failed` РАЗДЕЛЁН по `orders.paid_at`: с ним «Деньги списаны, билеты не
  оформлены» (красный), без него «Платёж не состоялся» (серый) — иначе журнал
  краснел на обычных неоплатах и настоящее ЧП в этой красноте теряется.
  **Возвраты в журнал продаж джойнятся ТОЛЬКО как `kind='ticket'`:** у возврата
  удержания номера того же билета, и без фильтра билет попадал в журнал дважды.
  Возвраты багажа (номера своих бланков) и удержания подтягиваются отдельными
  запросами — багаж пометкой в колонке «Багаж» и в статусе, удержание —
  колонкой «Возврат удержания»; до этого ни того, ни другого в журнале не было
  видно вовсе. Цвет в `SiteRefundsReport` — та же семантика (деньги не отданы →
  красный, нет чека → оранжевый, норма → сиреневый).
  **Наведение мыши не перекрашивает строку** (`inset box-shadow`, а не
  `background`): прежнее правило `tr:hover td` стояло после `row-*` с той же
  специфичностью и гасило подсветку именно у той строки, которую разглядывают.
  Заметность даёт цветная полоса слева (`border-left: 4px` у первой ячейки) —
  её видно и при прокрутке вбок, когда столбец статуса ушёл за край. Печать
  отчёта (в legacy она была) — `@media print` в `style.css`:
  `print-color-adjust: exact`, иначе браузер не печатает фоны и отчёт выходит
  без подсветки.
  Сводная «по станциям и агентам» из in.php перенесена отдельным отчётом
  **`station-sales`** (19 денежных колонок + станция, исходные условия
  `SALE_ALL`, включая `AGENTBACK.PRICE_PL_ISX` без багажа). Копия продаж —
  `ais.station_sales` (индексируемые поля + полный `raw_data`, глобальный
  ключ из 8 полей PK SALE, как в legacy). Источник сайта — Postgres `site`.
  Сбор: `station-sales:sync` ставит по заданию на станцию; ofelia ежеминутно
  проверяет расписание через `--scheduled` и запускает `station-sales:work`. HTTP только
  ставит задания и читает статус. Firebird читает всю порцию одним запросом
  за 10 календарных дней по умолчанию. Дочерний CLI-процесс пишет строки
  во временный файл с дедлайном 25 с. Период публикуется атомарно из staging,
  прогресс по датам сохраняется в БД. Актуальность обновляется после
  успешного сбора всего текущего окна. Автозапуск по умолчанию в 07:00 по
  серверу. В /settings редактируются время, выключатель, глубина окна
  **`station_sales_lookback_days`** (90 дней по умолчанию) и размер порции
  **`station_sales_chunk_days`**. По возврату сверяется исходная продажа любой даты.
  Разовый перенос архива: `station-sales:import-legacy` (1000 строк/порцию,
  курсор на диске, новые данные не перезаписывает, актуальность не ставит).
  Право запуска сбора — `report:station-sales.refresh`, просмотра — `.view`;
  дополнительные права отчёта задаются в его `meta.permissions`, каталог
  ролей подхватывает их автоматически. Подробнее — [docs/STATION_SALES.md](docs/STATION_SALES.md).
- **Заказ оплачен, билетов нет: статус НЕ портим и платёж можно отменить
  вручную** (разобрано 16.11.2026 по заказу
  `01a1e420-6c63-734c-b389-42c9b7037cca`: станция Мценск была недоступна в
  момент дооформления, 486,26 ₽ списаны, билетов нет).
  **Что было не так.** `OrderService::confirm` при любой ошибке, кроме
  конфликтов продажи, писал заказу `failed`. Из-за этого заказ выпадал
  сразу из двух путей: покупатель не мог дооформить его по напоминанию
  («Заказ имеет недопустимый статус» — в журнале десять таких подряд), а
  команда `orders:cancel-abandoned` его не видела, потому что отбирала
  только `payment_registered`/`paid`. Деньги оставались у нас молча.
  **Исправлено тремя вещами:**
  - `OrderService::TEMPORARY_CODES` (`station_unavailable`,
    `sales_api_unavailable`, `bad_response`) — при временной помехе статус
    НЕ меняется, пишется только `status_reason`. Деньги у нас, оформление
    просто не состоялось сейчас;
  - `SalesApiClient` превращает `ConnectionException` в
    `SalesApiException('sales_api_unavailable')` — раньше отсутствие ответа
    давало покупателю «cURL error 7», а заказу неопределённое состояние;
  - `AbandonedPaymentService::candidates()` берёт ещё и `failed` с
    заполненным `paid_at` без билетов — страховка на любую причину порчи
    статуса.
  **ЛОВУШКА `reverse`: по уже СПИСАННОМУ платежу шлюз проводит отмену как
  ВОЗВРАТ.** Порядок у нас правильный — сначала `reverse.do` (она мягче:
  деньги возвращаются без отдельной операции по карте), при отказе
  `refund.do`. Но вызов отмены по завершённому платежу проходит БЕЗ ошибки,
  а заказ в шлюзе получает статус 4 («возврат проведён») и
  `refundedAmount` на всю сумму. Проверено на проде 16.11.2026 (заказ
  01a1e420-…, 486,26 ₽): наш код записал «Платёж отменён», а шлюз показал
  возврат. Наши платежи одностадийные и списываются сразу, поэтому на
  практике это почти всегда возврат. Поэтому ЧЕМ ЗАКОНЧИЛОСЬ, спрашиваем
  у шлюза (`AbandonedPaymentService::wasRefunded`) и пишем по факту:
  кассиру и покупателю важно, увидят ли они отдельную операцию по карте
  и когда придут деньги.
  **Логика отмены платежа теперь ОДНА** (`AbandonedPaymentService`) на два
  пути: команду по расписанию и кнопку «Отменить платёж и вернуть деньги»
  в АИС (`POST admin/refunds/cancel-payment`, право
  `back-ticket.refund`, с кодом подтверждения). Расходиться им нельзя:
  отмена платежа должна выглядеть одинаково, кто бы её ни запустил.
  Карточка `/back-ticket` для такого заказа показывает состояние
  **`unfinished_payment`** (деньги списаны, билетов нет) с причиной из
  `status_reason` и кнопкой; если шлюз говорит, что денег у нас нет,
  кнопка не показывается вовсе. Ждать автоматику кассир не обязан: она
  ходит раз в 15 минут и не раньше часа с момента заказа
  (`ORDER_ABANDON_AFTER_MINUTES`).
- **Операции возврата НЕ ЗАДВАИВАЮТСЯ** (исправлено 16.11.2026 по заказу
  `01a1d671-…`: пять нажатий «вернуть удержание» дали пять записей
  `penalty` по 8,95 ₽, все `bank_failed` — журнал возвратов распух, денег
  покупатель не получил).
  - **Замки на операцию.** `Cache::lock('refund-blank:{order}:{serial}:{number}')`
    у возврата билета и багажа, `Cache::lock('refund-penalty:{id}')` у
    удержания, `Cache::lock('refund-receipt:{id}')` у ручной фискализации.
    Двойной клик больше не уходит на станцию и в шлюз дважды.
  - **Повтор после отказа банка НЕ создаёт новую запись:**
    `confirmPenalty` берёт существующую незавершённую строку (деньги не
    ушли) и пробует платёж по ней снова, считая попытки в
    `legacy.attempts`. У билета и багажа от дублей защищает уникальный
    индекс, у удержания его нет (он частичный, `where kind <> 'penalty'`,
    ради частичных возвратов) — поэтому только так.
- **При отказе банка сотрудник видит ВСЮ технику** (`refunds.bank_response`,
  jsonb): код и класс ошибки, что отправляли (сумма в рублях и копейках,
  вид операции, номер платежа) и снимок состояния платежа в шлюзе (статус,
  `paymentState`, сколько уплачено/возвращено/доступно). В `bank_error`
  остаётся только короткий текст, а он у шлюза один на все случаи —
  «Системная ошибка.», и по нему причину не найти. В карточке это
  раскрывается кнопкой «Подробности отказа».
  **Чем на самом деле был вызван отказ «код 7»** (разобрано 16.11.2026):
  НЕ давностью платежа. Возврат, в отличие от отмены, шлюз принимает и
  через дни — тот же возврат удержания прошёл спустя 67 часов, как только
  сумма стала правильной. Отказ давала **потерянная копейка**:
  `floor(8.95 * 100)` = 894 при доступных 895, то есть мы просили сумму,
  оставляющую одну копейку «хвоста», — такую операцию эквайер не
  принимает. Ни одна из успешных операций такого остатка не оставляла.
  В шапке карточки показывается доступный к возврату остаток и состояние
  платежа; предупреждения «с оплаты прошло N часов» там СОЗНАТЕЛЬНО нет —
  оно вводило в заблуждение.
- **ЛОВУШКА КОПЕЙКИ: рубли в копейки переводятся ТОЛЬКО round.**
  `(int) floor(8.95 * 100)` даёт **894** — в двоичной арифметике это
  894.9999…, и покупателю уходило на копейку меньше, чем написано в
  карточке и в чеке. На проде это задело **7297 операций возврата из
  100 501** (7%): например 302,09 ₽ уходили как 30208 копеек. Мало того,
  именно эта копейка и была причиной пяти отказов «код 7» при возврате
  удержания: 894 из доступных 895 оставляли копеечный «хвост», и эквайер
  такую операцию отклонял (после исправления возврат прошёл сразу).
  Исправлено в трёх местах: админский возврат, возврат по коду и
  регистрация платежа заказа (`OrderService`). Сами СУММЫ по-прежнему
  считаются формулами legacy (там floor в `refundAmount` сознателен) —
  round касается только перевода в копейки.

  например, нет интернета, а покупатели просят деньги). Деньги возвращаем

  `refunds.station_annulled_at`, `station_annul_pending`,
  `station_annul_attempted_at`, `station_annul_error`,
  `station_backdated_at` (миграция `2026_11_16_000006`; прежним возвратам
  `station_annulled_at` проставлен из `created_at` — они аннулированы в
  момент создания).

  станция не подскажет процент, а место останется занятым; кассир жмёт

  станции»**: пока возврат в этом списке, место на рейсе числится
  проданным. В отчёте «Возвраты сайта» у таких строк своё состояние и своя
  подсветка **`row-station`** («Не аннулирован на станции») — жёлтый не
  годится: в журнале продаж он значит «ожидает оплаты», и легенда

- **Перенос даты возврата в журнале станции** — выключатель
  `refund_station_backdate` в «Настройках сайта» (по умолчанию ВЫКЛЮЧЕН).
  Включённый — при досылке `sales-api` правит `DATESALE`/`TIMESALE` у
  созданных записей возврата на дату, когда деньги реально вернули
  (`BusterGateway::backdateRefundRows`, параметр `backdate` у `POST
  /refunds`, только с `admin_mode`).
  **Что надо знать про эту правку (проверено по самой базе):**
  - вендорная процедура дату НЕ принимает: `KS_ANN_TICKET_FROM_AW` →
    `KS_ANN_TICKET` → `KS_INSERT_TO_SALE` пишет `current_date, current_time`.
    Поэтому только UPDATE после аннулирования;
  - `DATESALE` и `TIMESALE` входят в **первичный ключ** SALE, то есть это
    правка ключа. Внешних ключей на SALE в базе нет (проверено), связи не
    рвутся; при совпадении ключа с существующей записью UPDATE отклоняется —
    тогда дата просто остаётся прежней, возврат от этого не ломается;
  - **финансовые итоги станции (КСР, таблица `KSRALLRECORD`) НЕ
    переносятся.** Их пишет триггер `SALE_FINKSR_AI0` при ВСТАВКЕ записи и
    по дате вставки, а UPDATE-триггер `SALE_FINKSR_AU0` срабатывает лишь в
    узком случае (`kkm_ok=0, recmove=2, type_tick=6`). Из КСР считаются
    `BALANCE`, `BALANCE_ATP` (расчёты с перевозчиками), `SVOD_ATP`,
    `MONTH_REP`, `DOHOD_KSR` и ещё около тридцати процедур — значит журнал
    и финитоги за два дня разойдутся на сумму возврата. Это написано в
    подсказке выключателя;
  - правятся ТОЛЬКО записи, созданные этой досылкой: отбор по номерам
    бланков, `TYPE_OPER <> 0` и времени не раньше начала операции (время
    берётся по часам станции, не нашего сервера). Дату и время сравниваем
    ОТДЕЛЬНО: складывать timestamp со time Firebird 2.5 не умеет.
  Проверено на тестовой базе станции (192.168.2.5/kromy): продажа
  14:52 → возврат денег 14:53 при «выключенной» связи → досылка 14:55;
  в журнале станции записи возврата (билет и багажная квитанция) встали на
  14:53, место освободилось, `updated_rows: 2`.
- **Аннулирование на станции АТОМАРНО: отказ по одному бланку откатывает
  всю операцию** (исправлено 17.11.2026 по заказу
  `c57035943d07716aebbe4384f0819f`, билет 112657019984/099900079,
  АДАМЕНКО, 6935 ₽). `KS_ANN_TICKET_FROM_AW` идёт по бланкам **в цикле** и
  обрабатывает каждый независимо: удачные аннулирует, по неудачным
  дописывает «#» и свой код в `ERR_CODE_S`. А `BusterGateway::refund`
  коммитил транзакцию **ДО** проверки `ERR_CODE_S` — то есть частичный
  успех оставался на станции, а наружу уходил полный отказ: бланк
  аннулирован, записи возврата нет, деньги покупателю не вернулись, место
  на рейсе освободилось. Теперь проверка стоит внутри транзакции, любой
  ненулевой код → `rollBack()` (автономных транзакций процедура не
  открывает, откат снимает и то, что она успела записать), а в ответе есть
  **результат по каждому бланку** (`blanks: [{serial, number, ok, error,
  price, penalty_percent}]`, и у отказа — в `details.blanks`).
  **Сообщение об отказе ОБЯЗАНО называть бланк:** «Билет не найден в БД
  вокзала» без номера читается про возвращаемый билет, а относилось к его
  багажной квитанции — на этом потеряли полтора часа.
- **ЛОВУШКА `total_refund <= 0` — это НЕ признак ошибки станции**
  (исправлено 17.11.2026, `App\Support\StationRefundResult`). Станция
  честно отдаёт ноль там, где по её ведомости возвращать нечего:
  **бесплатная багажная квитанция** (`price_bag = 0`) и **полное
  удержание**. Проверка «сумма больше нуля» бросала исключение уже ПОСЛЕ
  аннулирования бланка и без записи возврата — то есть ровно теряла
  возврат. С этого и началась авария 17.11.2026: кассир нажал «Вернуть
  багаж» у билета с бесплатным багажом, станция квитанцию аннулировала и
  ответила нулём, мы сочли это ошибкой и ничего не записали; следующий
  возврат билета ушёл на станцию вместе с уже аннулированной квитанцией,
  получил отказ по ней — и отменил билет без денег покупателю.
  Признак успеха — **принятые станцией бланки**
  (`StationRefundResult::assertAllBlanksAnnulled`), и проверка стоит во
  ВСЕХ путях: админский возврат, возврат багажа, возврат по коду и из
  кабинета (`RefundService`), досылка аннулирования, команда
  `refunds:annul-baggage`. Фронты `total_refund` не читают вовсе.
- **Состояние бланка спрашиваем у СТАНЦИИ, а не только у своей таблицы**
  (sales-api `GET /blanks?awtcod=&date_start=&blanks[]=…`, только чтение).
  Своих `refunds` недостаточно: записи может не быть при аннулированном
  бланке (см. выше), а бланк мог вернуть **кассир станции** — тогда деньги
  покупателю выданы там, и возврат на карту будет вторым. Кто аннулировал,
  видно по `SALE.AWTCODSALE` — это код агента: **9984 — наш сайт,
  5701 — кассы Орла, 9900 — другой интернет-агент** (проверено на боевых
  возвратах). `date_start` обязателен к передаче по смыслу: журнал SALE
  станции — миллионы строк за годы.
- **Карточка возврата при отказе станции больше не тупик.** Было одно
  состояние `station_rejected` на все случаи, и кассир не мог ничего
  сделать. Теперь отказ разбирается (`AdminRefundService::stationRejectedState`):
  - бланк аннулирован **НАШИМ агентом**, записи возврата нет → состояние
    `station_already_annulled` и кнопка «Вернуть деньги (на станции уже
    аннулирован)» (`already_annulled: true` у `admin/refunds/confirm` →
    `confirmAlreadyAnnulled`). На станцию не идём вовсе,
    `station_annulled_at` берётся **из журнала станции**, а не `now()`:
    бланк аннулирован тогда, и в отчётах должна стоять та дата.
    `station_annul_pending` НЕ ставится — досылать нечего. Процент станция
    подсказывает своим `PROC_BACK`;
  - аннулировала **КАССА станции** → кнопки возврата нет сознательно:
    сначала сверка, деньги скорее всего выданы там;
  - бланк действует, отказ про другое (ведомость закрыта, рейс ушёл) →
    как раньше, но с перечнем отклонённых бланков.
  Серверная проверка обязательна: `confirmAlreadyAnnulled` сам смотрит
  журнал станции, обойти обычный путь этой кнопкой нельзя — как и у
  «возврата без станции» (`assertStationUnavailable`).
- **В списке билетов заказа видно состояние НА СТАНЦИИ.** Билет,
  аннулированный на станции без записи возврата у нас, показывался
  «действует» — ровно наоборот тому, что есть. Теперь у него состояние
  `annulled_no_money` («на станции аннулирован, ДЕНЬГИ НЕ ВОЗВРАЩЕНЫ»,
  красным): это тот же класс ЧП, что «деньги у нас, билета нет».
  Состояние бланков заказа берётся **одним запросом на заказ**
  (`AdminRefundService::stationBlanks`, память в свойстве по id заказа) —
  карточка спрашивает его в трёх местах.
- **`blanksToAnnul` пропускает квитанции, аннулированные НА СТАНЦИИ**, а не
  только те, по которым есть наша запись: иначе возврат билета упирается в
  уже аннулированную квитанцию и не проходит вовсе (именно это и
  заблокировало возврат АДАМЕНКО). А `baggageToRefund` не возвращает деньги
  за багаж, аннулированный **чужим** агентом (касса выдала деньги сама);
  аннулированный НАШИМ агентом без записи у нас из суммы НЕ вычитается —
  денег по нему покупатель не получал.
- **Отказ станции по её правилам — НЕ ошибка приложения.**
  `BusterException` («ведомость закрыта. Нет разрешения на возврат после
  отправления», «билет не найден в БД вокзала», «место уже продано»)
  логируется одной строкой `NOTICE` без стектрейса (`reportable` в
  `sales-api/bootstrap/app.php`, возвращает false). Прежде каждый такой
  отказ писал в ERROR девять килобайт стектрейса — ловилось на проде
  16.11.2026. **Важно помнить:** `admin_mode` обходит только НАШУ проверку
  IS_PRN, у станции свои правила (закрытая ведомость, запрет возврата после
  отправления), и их не обойти ничем — такой билет возвращают на станции
  вручную.
- **Админский возврат** (перенос `ais/back_bilet.php` 1:1, см. «Правила» об
  упрощениях): backend `POST /api/v1/admin/refunds/inspect|confirm|repair` +
  страница ais-spa `/back-ticket` (vite-proxy `/site-api` → web). Отличия от
  возврата по коду: без дедлайна и после отправления рейса (`admin_mode` в
  sales-api /refunds пропускает проверку IS_PRN — как legacy), сверка оплаты
  `getOrderStatusExtended` до возврата, процент удержаний выбирает админ
  (0/5/15/25 + рекомендуемый от станции; на вендорную ведомость процент НЕ
  влияет — в legacy `shtraf` до KS_ANN_TICKET_FROM_AW не доходил), починка
  зависшего возврата денег. **Багажные квитанции аннулируются ВМЕСТЕ с
  билетом** (`blanksToAnnul`): на станции это самостоятельные бланки
  категории 9, и `KS_ANN_TICKET_FROM_AW` аннулирует ровно то, что ей
  передали. В legacy их номера лежали в ключе `BAGAJ` каждого билета
  (`ORDERS.BILETS`, пишется в `end_buy`) и дописывались в `I_N_TICKET` в
  `tickets_back` (`ais/api/api2.php`) — то же сделано и здесь, и в возврате
  по коду (`RefundService`). Без этого возвращалось только место: деньги за
  багаж покупателю уходили (сумма считается с багажом), а в ведомости
  станции багаж оставался проданным — ловилось на проде 16.11.2026
  (билеты 112657019984/159900159 и /159900178). Сверено по данным станции:
  у боевых legacy-возвратов 12–15.11 багажный бланк аннулирован всегда.
  **Сумма считает только НЕВОЗВРАЩЁННЫЙ багаж** (`baggageToRefund`):
  возврат одного багажа — наша новая возможность, которой в legacy не было,
  и без поправки деньги за уже возвращённую квитанцию ушли бы второй раз.
  Там же: возврат билета целиком закрывает отдельный возврат его багажа
  (карточка пишет «возвращены вместе с билетом», `confirmBaggage`
  отказывает), а `findRefund` фильтрует `kind=ticket` — у возврата
  удержания номера того же билета.
  Возвраты, прошедшие ДО этого исправления, дочищает команда
  `php artisan refunds:annul-baggage` (backend): аннулирует на станции
  оставшиеся багажные бланки и пишет `refunds` kind=baggage с **нулевой
  суммой** и пометкой `annulled_later` — деньги за багаж покупателю уже
  вернулись в составе билета, второй раз их не возвращаем и чек не пробиваем.
  Возвраты, перенесённые со старого сайта, команда ПРОПУСКАЕТ (`legacy` не
  пуст): там legacy аннулировал багаж сам.
  **Отметка об аннулировании бланка не считается недочётом в отчётах:**
  строка с нулевой суммой (`refunds:annul-baggage`) не красится оранжевым
  «нет фискального чека» — чека по ней и не должно быть, в «Возвратах сайта»
  у неё статус «бланк аннулирован, деньги возвращены с билетом» и прочерк в
  колонке чека, а в журнале продаж она не попадает в счётчики проблем.
  **Карточка возврата открывается и по номеру БАГАЖНОЙ квитанции**
  (`findTicket` ищет её среди `baggage_tickets` билета): так ведёт ссылка
  «Бланк» из отчёта возвратов, и раньше она выдавала «Нет билетов с такими
  номерами в заказе». Карточка показывает билет-владелец и говорит, по какой
  квитанции её открыли (`opened_by_baggage`).
  **Возврат с нулевой суммой — отметка, а не возврат:** `Refund::withheld()`
  возвращает 0 при `amount <= 0`, иначе строка «багаж, сумма 0» выглядела как
  возврат со 100% удержанием, карточка предлагала «вернуть удержание», и шлюз
  отвечал «Сумма возврата превышает сумму списания» (ловилось 16.11.2026).
  `confirmPenalty` такую строку отклоняет отдельным сообщением.
  **ЛОВУШКА уникальности `refunds`:** ключ (заказ + серия + номер + вид)
  рассчитан на «один возврат на бланк», и для частичных удержаний он не
  годится — второй частичный возврат падал на нём с «Server Error»
  (ловилось на проде 16.11.2026: вернули 2.00 из 5.57, остаток 3.57 отдать
  не получалось). Индекс сделан ЧАСТИЧНЫМ — `where kind <> 'penalty'`
  (миграция `2026_11_16_000002`): у билета и багажа уникальность осталась
  (она закрывает повторный возврат того же бланка), у удержания её
  заменяет проверка остатка в коде.
  **Удержание возвращается ЧАСТЯМИ** (`confirmPenalty` принимает `amount`,
  в карточке у строки возврата поле суммы с остатком по умолчанию): кассиру
  нередко надо отдать покупателю часть удержания, а остальное позже. Остаток
  считает `penaltyLeft` — сумма успешных и ожидающих банк строк удержания;
  отказ банка остаток НЕ уменьшает, иначе неудачная попытка «съедала» бы
  удержание.
  **Позиции чека возврата — только то, за что отдаются деньги**
  (`RegisterRefundReceipt::items`): у возврата удержания позиция называется
  «Удерж. …» (была «Билет …»), а нулевые позиции не печатаются вовсе — в чеке
  возврата одного багажа стояла лишняя строка «Билет … 1 x 0.00».
  **Починить зависший возврат денег можно по ЛЮБОЙ строке** (`repair`
  принимает `refund_id`, кнопка «Вернуть по банку» в списке возвратов
  заказа): зависает не только возврат билета — у возврата удержания и
  возврата багажа свои обращения к шлюзу, а у багажной квитанции нет номера
  билета, по которому раньше искался возврат. Отказ шлюза теперь пишется в
  лог целиком (`Шлюз отказал в возврате платежа`): в `bank_error` попадает
  только короткий текст вроде «Системная ошибка.», и разбираться потом было
  не по чему. Формула суммы — как в back_bilet (number_format,
  округление round), НЕ как в backbycode (floor). Права сотрудника:
  `back-ticket.inspect` на поиск билета, `back-ticket.refund` и
  `back-ticket.repair` — с кодом подтверждения. **Запросы страницы идут
  через общий слой** (`siteApi.refundAction` → `http.js`), своего `fetch`
  у неё быть не должно: код подтверждения спрашивает именно слой запросов
  (ответ `need_confirm`), а со своим `fetch` сервер отвечал «Действие
  требует подтверждения кодом.» и кнопки возврата денег просто не
  работали — ловилось на проде 16.11.2026.
- **`ais-spa/`** — SPA отчётов АИС (Vue 3 + Vite, :3001 dev): перенос из устаревшего
  репозитория `avtovokzal_ais_spa` (тот был под legacy apiv2). `/api` → ais_web через
  vite-proxy.
  **Новая сборка доезжает до сотрудника сама** (`src/version.js`): vite кладёт
  рядом со статикой `version.json` с меткой сборки и подставляет ту же метку
  в код (`__APP_VERSION__`), приложение опрашивает файл раз в 2 минуты и при
  возврате к вкладке. Разошлись — на ПЕРЕХОДЕ между страницами идёт
  `location.replace` (безопасная точка: посреди заполненной формы возврата
  терять введённое нельзя), а пока сотрудник на месте, внизу висит полоса с
  кнопкой «Обновить страницу». Проверка ходит с `cache: 'no-store'` — иначе
  сама приходит из кэша; в dev слежение выключено (там этим занимается HMR).
  Зачем: SPA живёт во вкладке неделями, и сотрудник работал в СТАРОЙ версии,
  не зная об этом — «не могу вернуть багаж» 16.11.2026 оказалось именно
  открытой старой версией страницы возврата.
- **Сотрудники АИС, роли и права** (в legacy авторизации не было вовсе —
  доступ закрывало ограничение по IP на nginx, и внутри сети отчёты и
  возврат билета открывал кто угодно с любой машины; переносить было
  нечего). Сотрудники, роли и сессии живут в **БД `ais`** (ais-api):
  таблицы `employees`, `roles`, `employee_role`, `employee_tokens`.
  - **Каталог модулей и прав — `shared/ais_permissions.php`** (как
    `shared/stations.php`): `config/ais_modules.php` обоих приложений
    делает `return require`. Ключ права — `<модуль>.<право>`
    (`pages.edit`, `back-ticket.refund`). Набор прав у модулей РАЗНЫЙ.
    Отчёты в каталоге НЕ перечислены: их модуль `report:<slug>` АИС
    собирает на лету из `config/reports.php` (`ModuleRegistry`), иначе
    список отчётов жил бы в двух местах. Новый отчёт появляется в
    редакторе ролей сам.
  - **Опасные права помечены в каталоге (`confirm`)**, а не в маршрутах:
    сервер отвечает 428 `need_confirm`, клиент спрашивает личный код
    сотрудника и повторяет запрос с заголовком `X-Confirm-Code`. Так
    список опасных операций не расходится с тем, что видит администратор
    в редакторе ролей.
  - **Роль «Администратор» системная** (`roles.is_system`): права не
    хранит и не редактируется — ей доступно всё, включая модули, которых
    ещё нет. Её создаёт МИГРАЦИЯ, а не сид: без неё первый `ais:admin`
    остался бы без роли.
  - **Первый администратор — `php artisan ais:admin <логин>`** (ais-api).
    Ею же сбрасывают пароль, когда он потерян; дальше сотрудников
    создаёт и сбрасывает любой администратор в АИС. Без `--password`
    пароль генерируется парольной фразой и печатается.
  - **Логин** нечувствителен к регистру и к пробелам по краям, состав
    символов НЕ ограничен (русские буквы можно): `login` как ввели +
    `login_normalized` для поиска (`App\Support\AisLogin`).
  - **Надёжность пароля — zxcvbn** (`bjeavons/zxcvbn-php`, перенос модуля
    из проекта `api.gotov.org`): считается стойкость к подбору, а не
    состав символов, поэтому фраза из слов одного регистра проходит, а
    «Пароль123!» нет. Плюс русский словарь (`RussianPasswordDictionary`)
    и проверка обеих раскладок (`gfhjkm` = «пароль»). `trim` и при
    установке, и при проверке. Длина и порог — `shared/ais_auth.php`.
  - **Три секрета у сотрудника, у каждого своя роль:** `password`
    (bcrypt), `confirm_code` — код подтверждения опасных действий
    (bcrypt, 3–20 любых знаков, никому не показываем), `fast_token` —
    токен быстрого входа по ссылке `?token=…`. Токен обязан
    ПОКАЗЫВАТЬСЯ владельцу, поэтому лежит в шифре Laravel, а искать по
    нему позволяет отдельный sha256 (`fast_token_hash`): Crypt у каждого
    шифрования даёт разный результат, индексом по нему не найти.
  - **Токен быстрого входа действует ТОЛЬКО из доверенных сетей**
    (`ais_auth.token_networks`, по умолчанию приватные диапазоны): он
    виден в адресной строке, в истории браузера и в журналах прокси.
    Пустой список = вход по токену выключен. SPA, увидев `?token=`,
    обменивает его на обычную сессию и СРАЗУ убирает из адреса — причём
    до монтирования приложения, иначе vue-router затирает наш
    `replaceState` и токен остаётся в истории.
  - **Сессия — своя таблица `employee_tokens`, не Sanctum:** её читает и
    backend (см. ниже), а хэш считается тем же sha256 без секрета
    приложения — иначе приложениям пришлось бы делить APP_KEY.
    **Токен несёт httpOnly-cookie `ais_session`, её ставит сервер:**
    сессия живёт месяцами (`session_idle_minutes` 90 дней, предельного
    срока нет), а localStorage и cookie из JS Safari/ITP стирает примерно
    через неделю — сотрудник разлогинивался бы сам (та же причина, что у
    кабинета сайта). `SameSite=Lax` закрывает CSRF. Мёртвые строки чистит
    `ais:prune-tokens` (ofelia, 04:35).
  - **`trustProxies(at: '*')` в ais-api обязателен:** без него
    `$request->ip()` равен адресу docker-сети, и проверка «из рабочей
    сети» либо не работает вовсе, либо разрешает кого угодно.
  - **Админские маршруты backend (`/api/v1/admin/*`) защищены тем же
    сотрудником**: middleware `ais.can:<право>` (`App\Services\AisAuth`)
    читает `employees`/`roles`/`employee_tokens` ПРЯМЫМ запросом в БД
    `ais` (соединение `ais` в `config/database.php`), а не по сети у
    ais-api: админку и backend открывают с одного домена, cookie приходит
    и туда, а лишний вызов с кэшем прав на каждый запрос не нужен.
    В эту базу backend пишет единственное — отметку обращения к сессии.

- **Мусор на входе не создаёт записей в журнале ошибок.** Правило общее:
  боты, сканеры и люди присылают в параметры что угодно, и от этого
  журнал расти не должен — иначе в нём не видно настоящих сбоев.
  Поэтому: ошибки проверки (`ValidationException`) и `HttpException`
  (404/403) Laravel не репортит сам, а **любой отказ API продаж с кодом
  4xx считается штатным** (`SalesApiException::$httpStatus` +
  `isExpected()`) — виноват запрос, а не система. В журнал по-прежнему
  попадают 5xx, отсутствие ответа, нераспознанный формат и конфликты
  продажи (`already_sold`, `sale_in_progress`, `concurrent_sale` — они
  про деньги покупателя). **502/503/504 без JSON — это ответ nginx, а не
  API продаж** (сервис перезапускается при деплое, не поднялся, не успел
  ответить), поэтому `SalesApiClient` даёт им `sales_api_unavailable`, а
  не `bad_response`: покупателю — понятный текст вместо «Некорректный
  ответ API продаж», а дооформлению оплаченного заказа — временная
  помеха, от которой статус заказа не портится
  (`OrderService::TEMPORARY_CODES`).
  **Вендорные коды проверяются границами** — `App\Support\VendorCode`
  (есть и в backend, и в sales-api): `min:1`, **`max:32767`**. В базе
  станции это **SMALLINT, а НЕ INTEGER** — проверено по `RDB$FIELDS`:
  `SHORT` у `EVRYRAICE.{AWTCOD,NAPCOD,RAICECOD,NOMKAT}`,
  `RAICELST.{AWTCOD,NAPCOD,RAICECOD}`,
  `TARIFS2D.{AWTCODE,NAPCODE,STATCODE,KATCODE}`,
  `TRACES.{AWTCOD,NAPCOD,STATCOD}`, `NAPLST.{AWTCOD,NAPCOD}` и
  `SALE.{N_PLACE,KATPAS,DOCUMCOD_PASS,GRAGD_ID,TYPE_TICK,WRKCOD}`.
  Значение вне диапазона Firebird встречает арифметической ошибкой
  «-303 numeric overflow» — то есть ответом 500 и девятью килобайтами
  стектрейса на один мусорный запрос. **ЛОВУШКА: переполнение даёт только
  БИНДИНГ параметра.** В литерале `where RAICECOD = 904407066` Firebird
  спокойно отвечает «0 строк», а `where RAICECOD = ?` с тем же значением
  падает — а наши запросы ходят именно параметрами. Проверено: 32767
  проходит, 32768 уже падает.
  Прежде предел стоял `2147483647` (комментарий утверждал «это INTEGER»),
  то есть дыра была в 65 тысяч раз шире нужного: 17.11.2026 обходчик
  открыл старую ссылку тарифа с `raicecod=904407066`, проверку int32 она
  прошла, и покупателю ушло «Server Error».
  Той же границей ограничены **место, код документа и гражданство** в
  продаже (`SaleController`, `StoreOrderRequest`, `SavePassengerRequest`):
  у `tickets.*.place` границ не было вовсе, а `N_PLACE` — тоже SMALLINT.
  Проверка стоит в ОБОИХ приложениях: к sales-api агенты ходят напрямую,
  его защита не может опираться на backend.
  **Проверка:** обстрелять оба API мусором (нули, буквы вместо чисел,
  числа вне int32, инъекции в параметрах, обрезанные ссылки, пустые тела
  POST, несуществующие пути) и убедиться, что размер `storage/logs`
  не изменился ни на байт, а рабочие запросы по-прежнему отдают 200.

  `PDOException` и бросает **`StationUnavailableException`**: sales-api

  WARNING «Связь с базой станции пропала» в момент, когда связь пропала,

- **Обрыв связи ПОСРЕДИ запроса — тоже «станция недоступна»**
  (`BusterConnection::guard`, 17.11.2026). `GatewayFactory` ловит
  `PDOException` только при СОЗДАНИИ соединения, поэтому понятный отказ
  503 `station_unavailable` получался лишь когда до станции не дошли
  вовсе. Если канал рвался уже после подключения, PDO бросал исключение
  из `select`/`execute`, и покупатель видел **«Server Error»**: так было
  17.11.2026 в 06:04 с «Болхов КП» — запрос рейсов висел 19 секунд и упал
  с `-902 Error reading data from the connection`, хотя сбой был
  единичный (соседние запросы шли по 170–620 мс).
  Теперь `select`/`execute` распознают обрыв по **классу SQLSTATE «08»**
  (`08006` = Firebird −902, `08003`, `08001`, `08S01`; плюс страховка по
  тексту) и бросают `StationUnavailableException`. Отметку «станция
  недоступна» в кэше это сознательно НЕ ставит: разовый сетевой сбой не
  должен на минуту закрывать живую станцию — в отличие от отказа при
  подключении, где пауза экономит обработчики php-fpm.
  **Настоящие ошибки станции не подменяются**: `-303 numeric overflow`,
  `-204 table not found`, отказы процедур по-прежнему идут наверх как
  `PDOException` и попадают в журнал (проверено).
  Там же `rollBack()` **молчит об обрыве**: откат на мёртвом соединении
  сам бросает исключение и подменял им настоящую причину, из-за которой
  откат и понадобился (сервер такую транзакцию всё равно отменяет сам).
  **У ais-api своя копия соединения** (`StationConnection`) — там этого
  разбора НЕТ, и обрыв посреди отчёта по-прежнему даёт ошибку сотруднику;
  отчёт открывает человек, который сам и запустил, так что это терпимо.
- **ЛОВУШКА: pdo_firebird НЕ поддерживает таймаут подключения.**
  `PDO::ATTR_TIMEOUT` он молча игнорирует (проверено: соединение с
  «чёрной дырой» висело больше двух минут), поэтому ожидание равно
  системному `connect()` — около двух минут при потерянных пакетах.
  Чем это кончается: 16.11.2026 с 20:10 до 20:23 пропала связь СО ВСЕМИ
  станциями (канал до `192.168.4.250`), запросы к ним заняли обработчики
  php-fpm целиком, и сайт начал отвечать «Server Error» даже там, где
  станции не нужны, — 9 записей «Некорректный ответ API продаж»
  (sales-api отдавал не-JSON, потому что его резал nginx), «cURL error
  52: Empty reply» и два письма о покупке БЕЗ PDF билетов (gotenberg не
  успел отрендерить печатную форму).
  **Но таймаут спасает только от ОБРЫВА канала.** У Кром порт отвечает
  мгновенно (на `192.168.4.250` слушает туннель), а отказ `connection
  rejected by remote interface` приходит **через 21 секунду** — это
  ответ с другой стороны, укоротить его нечем. Запросов к такой станции
  идёт по 150–190 в час, то есть обработчик php-fpm занят ею почти
  постоянно. Поэтому к станции, которая только что отказала,
  `GatewayFactory` **минуту не ходит вовсе** (`RETRY_PAUSE_SECONDS`,
  отметка `station-offline:<awtcod>` хранит `retry_after`): покупатель
  получает «автостанция недоступна» сразу, а не через 21 секунду. Цена —
  станция, ожившая секунду назад, числится недоступной ещё до минуты.
  Проверено: первый отказ — по таймауту, следующие в паузе — мгновенно и
  без записей в журнал, после паузы подключение проходит и пишется
  «восстановлена».
  Перед созданием PDO идёт **TCP-проба** с коротким таймаутом
  (`BusterConnection::assertReachable` в sales-api,
  `StationConnection::assertReachable` в ais-api): не дошли — бросаем
  `PDOException`, и дальше всё идёт обычным путём, то есть станция
  объявляется недоступной. Проба именно TCP: разорванный канал виден уже
  на ней, а отказ самой базы («connection rejected by remote interface»
  у Кром, неверный пароль) — это ответ станции, его разбирает PDO.
  **Сколько ждать — настройка в АИС** («Настройки» →
  «Ожидание связи с базой станции», ключ `station_connect_timeout`,
  по умолчанию 5 с, границы 1–60): станции сидят на разных каналах (VPN,
  туннель, прямой IP), и «сколько это нормально» знает тот, кто видит
  сеть. Её читают sales-api (`App\Services\SiteSettings`) и ais-api
  (своя копия класса) ПРЯМЫМ запросом к таблице `settings` БД сайта —
  соединение `site`, кэш 30 с, как у справочника станций; недоступна
  настройка — работает значение из `config/buster.php` (sales-api) и
  `config/stations_db.php` (ais-api). Таймаут применяется в ТРЁХ местах:
  продажа и поиск рейсов (`GatewayFactory`), кнопка «Проверить» в
  справочнике станций (`ConnectionTester`) и отчёт «Агентские билеты»
  (`AgentsReport` — он идёт по всем станциям хозяйства, и без
  ограничения один пропавший канал задерживал бы его на две минуты за
  станцию).
  **Это первая настройка типа `int`**: у каталога `config/settings.php`
  появились поля `min`/`max`/`unit`, значение зажимается в границы в
  `SettingService::cast` (ноль означал бы «не ждать вовсе» — ни одна
  станция не ответит), а страница АИС рисует для такого типа числовое
  поле. Состав полей задаёт сервер — границы на фронте второй копией не
  держим.

  «Забыли пароль». В обоих случаях гасится `legacy_password` (иначе
  прежний пароль продолжал бы пускать — ровно эту дыру имел legacy) и
  закрываются все сессии. **Сам пароль в журнал не пишется** — только
  отметка, задан он или сброшен.
  **Смена e-mail меняет и состав видимых покупок** (кабинет видит заказы
  по `orders.email`), поэтому в ответе прямо пишется, сколько заказов
  станет видно; адрес, назначенный сотрудником, считается подтверждённым,
  а строка `user_identities` с `provider=password` переписывается на новый
  логин.
  **Ловушки производительности (не вернуть обратно):**
  - в `union` для списка попадают ТОЛЬКО колонки. Подзапрос способов
    входа (`string_agg` по `user_identities`) в `select` вычислялся до
    сортировки и `limit`, то есть для всех 84 тыс. кабинетов, и открытие
    списка стоило 1,2 с; теперь способы входа и счётчики покупок
    дописываются к показанным 25 строкам (76 мс);
  - `total` считается двумя `count`-запросами, а не `count(*)` по
    объединённой выборке — иначе тот же union прогоняется дважды;
  - фильтр «с покупками» сравнивает адрес через `in (подзапрос)`, а не
    коррелированным `exists`: заказов без кабинета сотни, подзапрос
    считается один раз (1,7 с → 0,4 с);
  - индексы: `users(created_at)`, `users(last_login_at)` и
    функциональные `lower(email)` у `users` и `orders` (сравнение адресов
    без учёта регистра обычным индексом не покрывается);
  - **массивы Postgres строкой собирать нельзя.** `where … = any('{a,b}')`
    падал с «malformed array literal»: в базе лежат адреса с кавычками,
    слэшами и переводами строк — со старого сайта приехали попытки
    инъекций в поле e-mail. Только параметры (`in (?, ?, …)`).
- **Вход в кабинет покупателя от имени сотрудника** (право
  `customers.impersonate`): АИС выдаёт одноразовый код (`Cache`, 2 мин),
  сотрудник переходит по ссылке `SITE_URL/auth/impersonate?code=…`,
  серверный маршрут Nuxt меняет код на токен Sanctum **своим** запросом и
  кладёт в ту же httpOnly-cookie `av_session`. Токен в адресную строку не
  попадает — он осел бы в истории браузера и в журналах nginx (та же
  причина, по которой в АИС запрещён `?token=` из интернета).
  Токен помечен способностью **`impersonated`**: срок — 30 минут от
  ВЫДАЧИ, а не по бездействию (`site.impersonate_ttl_minutes`, проверка в
  `AppServiceProvider`), сайт показывает полосу `ImpersonationNotice`
  (не «липкая» — шапка уже `sticky top-0`), а изменения запрещены
  middleware **`not.impersonated`**: покупка, подтверждение и отмена
  заказа, возврат по коду и из кабинета, профиль, пароль, e-mail,
  сохранённые пассажиры. Выход (`auth/logout`) разрешён — иначе из режима
  было бы не выйти.
  **ЛОВУШКА `can()` (ломала покупку ВСЕМ):** признак режима проверяется
  ТОЛЬКО через `App\Support\ImpersonationToken::is($token)` — явное
  наличие способности в списке. `$token->can('impersonated')` для этого
  негоден: обычный токен кабинета создаётся без списка способностей, то
  есть с `['*']`, а `can()` у Sanctum на `*` отвечает «да» на любой
  вопрос. Из-за этого КАЖДЫЙ вошедший покупатель считался сотрудником в
  чужом кабинете: ему показывалась оранжевая полоса, покупка, возврат и
  правка профиля отвечали 403, а сессия жила 30 минут вместо полугода
  (сломано деплоем 16.11.2026 12:57, замечено по полосе у обычного
  покупателя, исправлено в тот же день). Проверка: токен с `['*']` и
  токен с `['impersonated']` рядом — признак должен отличаться.
  **ЛОВУШКА guard:** в middleware стоит `$request->user('sanctum')`, а не
  `$request->user()`. Публичные маршруты (покупка, отмена заказа) идут без
  `auth:sanctum`, и guard по умолчанию отдаёт `null` даже при присланном
  Bearer-токене — покупка из чужой сессии проходила мимо запрета (ловилось
  при проверке: `POST orders` отвечал 422 вместо 403), тогда как сам
  контроллер берёт покупателя именно из `user('sanctum')`.
  **Офлайн-копии билетов в таком режиме не создаются** (`useOfflineTickets`
  проверяет признак): в них ФИО и номера документов, и оставлять их в
  IndexedDB на машине сотрудника нельзя.
- **Работа в АИС от имени другого сотрудника** (право
  `employees.impersonate`, с кодом подтверждения; кнопка «Войти как» на
  `/employees`). Зачем: роль на словах не проверишь, а «у меня нет этого
  отчёта» — самая частая жалоба; быстрее один раз увидеть АИС его
  глазами.
  Администратор получает ОТДЕЛЬНУЮ сессию сотрудника
  (`employee_tokens.kind = impersonate`, `impersonated_by`, `expires_at` —
  час от выдачи, `ais_auth.impersonate_minutes`), а его собственная сессия
  **не гасится**: её токен лежит в httpOnly-cookie
  `ais_session_admin` (`ais_auth.impersonator_cookie`), по ней работает
  возврат к себе (`POST impersonation/stop`). Поэтому ни чужой пароль, ни
  повторный вход не нужны. При старте и возврате SPA **перезагружается**
  (`location.assign`): у сотрудника другие права, другое меню и другой
  список отчётов — посмотреть на это и зовут.
  Журнал — таблица `employee_impersonations` (кто, кого, когда, ip,
  когда завершил): сессия при выходе удаляется, а запись должна остаться.
  `last_login_at` сотруднику НЕ двигаем — он не входил.
  **Режим наблюдательный, и это проверяется в ДВУХ приложениях:** в
  ais-api middleware `employee.not-impersonated` пропускает только
  безопасные методы, запуск отчёта (`reports/*/run` — он POST, но ничего
  не меняет), выход и возврат к себе; в backend `AisEmployeeCan`
  разрешает лишь права `view` и `inspect`. Второе обязательно: cookie
  сессии одна на SPA и оба API, иначе из такой сессии можно было бы
  править страницы сайта от имени сотрудника. Опасные действия закрыты и
  сами собой — код подтверждения чужого сотрудника администратору
  неизвестен.
  Запрещены «матрёшка» (вход от имени из режима), вход в себя и вход в
  отключённую запись; подложенная чужая cookie возврата не пускает в
  чужую учётную запись (сверяется `impersonated_by`), а сессия «от имени»
  при такой попытке гасится.
  **ЛОВУШКА Postgres:** `UPDATE … ORDER BY … LIMIT 1` (закрытие записи
  журнала) в Postgres не работает вовсе — это MySQL-расширение; надо
  найти строку и сохранить модель.

### Валидация данных пассажира (не ослаблять!)
- **Дата рождения: не старше 100 лет и строго в прошлом.** Правило вендорной
  процедуры `KS_CONTROL_BIRTH_PAS`: `birth_day >= Current_Date - 100 лет` И
  `birth_day < Current_Date`. Проверяется ДО оплаты (`StoreOrderRequest`,
  `SavePassengerRequest`, `DateInput` на фронте) — раньше стояло
  `after:1900-01-01`, и дата вроде 12.12.1922 ловила отказ станции «Дата
  рождения … указана неверно» уже на оформлении, когда деньги списаны.
- Правила серии/номера документа сняты 1:1 с вендорной процедуры
  **`KS_CONTROL_DATA_PAS`** (исходник — `docs/buster-procedures/`) и выполняются
  ДО оплаты: `backend/app/Services/PassengerDocument.php` + `StoreOrderRequest::after`.
  При изменениях сверять скриптом (18 кейсов против живой процедуры — см. историю
  коммита «Валидация документов по правилам станции»).
- ФИО: BUSTER не проверяет и молча режет до 20/14/14 — лимиты и фильтр символов
  (буквы/дефис/пробел/апостроф) держим на backend. **Ё всегда заменяется на Е**
  (`OrderService::normalizeName`) — буква Ё ломает вендорный софт станции.
- Справочник гражданств — таблица `citizenships` (коды COUNTRIES_TABLE, 185 = Россия),
  сид `CitizenshipSeeder` из `database/data/citizenships.json`. В кэш класть только
  массивы: Eloquent Collection в database-кэше десериализуется в incomplete class.

### Legacy через ODBC-shim

Боевой код работает в контейнерах `legacy`/`legacy_site` **без правок**: класс `db_work`
написан под ODBC, а `docker/legacy/odbc-shim.php` (`auto_prepend_file`) эмулирует `odbc_*`
через нативный Firebird и перенаправляет все подключения на контейнер `firebird`.

**Ловушки shim, уже учтённые (не сломать при правках):**
- Явные транзакции: `ibase_trans` + `commitT` — без коммита INSERT/UPDATE не сохраняются
  (симптом: оплата прошла, а заказ «не оформлен»).
- TIMESTAMP теряет миллисекунды при биндинге ibase → таймстемпы **инлайнятся прямо в SQL**.
- `charSet` берётся из DSN (как боевой драйвер): конфиги с `charSet=UTF-8` отдают UTF-8,
  без — сырой WIN1251 (страница сама делает `iconv`).
- **Таймзоны:** Firebird и PHP должны быть в **+3** (`TZ=Europe/Moscow`), иначе payconfirm
  падает на сверке времени резерва.

## Базы

- **PostgreSQL** (`db`) — наши данные (`site`, `ais` после переноса), `./data/postgres`.
  **Сервер живёт в Europe/Moscow** (`command: postgres -c timezone=…` в compose,
  плюс `TZ` контейнера): `now()`, журнал и вывод timestamptz — в +3.
  **ЛОВУШКА:** Eloquent пишет даты строкой БЕЗ смещения, поэтому пояс СЕССИИ
  решает всё — каждое приложение задаёт его ЯВНО в своём `config/database.php`
  (все четыре — `Europe/Moscow`). Положись они на умолчание сервера, их
  timestamptz уехали бы на 3 часа при смене пояса сервера. Проверка:
  `show timezone` из каждого контейнера.
  **sales-api и kkm-api раньше жили в UTC — переведены на +3 15.11.2026.**
  У sales-api это не только про свои таблицы: он сравнивает времена рейсов
  BUSTER (московские wall-clock) обычными `date()`/`time()` — сегодняшняя
  дата в поиске рейсов и отсечка «не ближе 2000 секунд до отправления», —
  и в UTC эти сравнения уезжали на 3 часа: в список попадали уже ушедшие
  рейсы, а с полуночи до трёх ночи «сегодня» оказывалось вчерашним числом
  (купить их всё равно не давал фронт, у него своя отсечка).
  **ЛОВУШКА:** пояс процесса Laravel выставляет из `config('app.timezone')`
  (`date_default_timezone_set` в LoadConfiguration), поэтому `TZ`
  контейнера на `date()` НЕ влияет — менять надо конфиг, а не compose.
  Данные, записанные до перевода, остались в UTC: это тестовые прогоны,
  исправлять их не стали.
- **Firebird 2.5** (`./databases`, восстановлены из бэкапов): `BUSTER` (buster.fdb, Красная
  Заря, вендорная), `ais` (ais.fdb), `site` (site.fdb).
  Восстановление: `gbak -c -n -o -user SYSDBA -password masterkey <файл.fbk> /firebird/data/<имя>.fdb`
  (`-n` обходит NOT NULL в вендорных бэкапах).

isql к нашим базам:
```bash
docker compose exec -T firebird /usr/local/firebird/bin/isql -user SYSDBA -password masterkey site
```
